# foo_navidrome

## Overview

foobar2000 v2 component: browse/stream from Navidrome / Subsonic-compatible servers. Cross-platform: macOS (shipped) and Windows x86/x64/ARM64EC (shipped). One `.fb2k-component` carries all platforms. Two entry points on macOS: **File › Open Navidrome Browser** and **Preferences › Media Library › Library viewers › Navidrome**.

## Working rule: every change is cross-platform

Any feature/fix touching shared or platform code must land on **both** macOS and Windows, not one — put logic in a shared file (`SubsonicTypes.h`, `SubsonicCore.h/.cpp`, `NavidromeBrowserModel.h/.cpp`, the SDK-glue `.cpp`s in `src/core/`) so both platforms consume the same implementation; only widget/wiring code stays platform-side. Checklist for any non-trivial change:
- **Both platforms**: implement/wire on macOS (`src/platform/mac/`) and Windows (`src/platform/win/`) — don't ship one-sided.
- **UI text**: every user-visible string goes through `tr()`/`trf()` (core), `trw()`/`trfw()` (Windows, `WinUi.h`) or `NDTr()`/`NDTrf()` (macOS, `MacI18n.h`), with its Spanish entry in `src/core/I18nSpanish.cpp` — `make test`/`mac-test` fail on a missing one (`make i18n-missing`). Log lines and Copy Diagnostics stay English.
- **Logging**: add `NAVIDROME_LOG`/`WARN`/`ERR` calls (see Gotchas) at meaningful steps (request sent, error, decision taken) — `scrubAuth()` any URL.
- **Tests**: add/extend a `TEST_CASE` in the matching `tests/*.cpp` topic file for any shared/SDK-free logic — all three toolchains run the whole folder. Then **actually run `make test`** (or `scripts/run-unit-tests.sh win`) after any logic change — shared or platform-side — before calling it done, not just after adding a new case. A change that "should still pass" is unverified until the suite says so.
- **Runtime UI smoke on both platforms**: `make win-build-launch && make win-ui-smoke` (Wine) and `make mac-vm-smoke` (macOS VM, builds in the guest with the debug log). For Windows GUI behaviour Wine can't show (Dark Mode, DPI scaling, native control theming) also run `make win11-smoke` / `make win11-ui ARGS='prefs …'` (real Windows 11 VM, `../windows-devbox`). These drive the real foobar2000 through a fixed scenario: open the browser, expand an artist, Enter on an album, then assert on the debug log, the process and crash reports, and save screenshots under `build/ui-test/`. All three platforms run through **one script, `scripts/ui-test.sh <wine|win11|mac> <scenario>`**: each scenario (`smoke`, `playqueue`, `search`, `cui`, `prefs`) is written once over a small per-platform driver (`<platform>_restart/key/cmd/log_from/shot/cfg_sql/…`). `make ui-compare ARGS='playqueue wine win11'` (add `mac`; `PARALLEL=1` runs them at once) prints a step-by-step matrix with `*` on rows where the platforms differ — run it for anything Windows-side, because Wine is an emulation and real Windows behaves differently in places (see Gotchas). When a change adds UI or a new code path, add a scenario step there (once, for every platform) and exercise the changed feature itself, not just "it loads". Anything that couldn't be checked goes in the PR.
- **Make/scripts**: if a new build/test/deploy step is needed, wire it into the `Makefile` + the relevant script (`run-unit-tests.sh`, `win-build-local.sh`, `mac-dev-build.sh`, etc.), not just run ad hoc. Same for any command reached for more than once that's long or easy to forget the flags of (a build+launch combo, a multi-step VM flow, a symbolizer invocation) — turn it into a `make` target instead of re-typing/re-deriving it each time.
- **Docs**: update this CLAUDE.md (architecture/decisions/gotchas as relevant) and README when user-facing.
- **No code comments**: `src/`, `tests/`, `scripts/`, `tools/`, the `Makefile` and `.github/workflows/` carry no comments (stripped 2026-10-09) — don't add any when writing or changing code: no `//`, `/* */`, `#`, `<!-- -->`, doc blocks or trailing notes, including inside code embedded in heredocs/strings (generated headers, `bash -c` bodies). A non-obvious *why* goes in this CLAUDE.md (Decisions/Gotchas) or the commit message; script help goes in its `usage()` heredoc. String-literal data (e.g. the ESLyric JS in `EsLyricScript.h`) and the markdown `##` headings inside `.github/ISSUE_TEMPLATE/` form values aren't comments — leave them.

## Cross-compatibility with other same-author components

Some standard foobar2000 SDK paths don't fit `navidrome://` tracks — there's no real file
backing them, so e.g. a `metadb_io_v2` tag write fails with "Tagging of this file format is not
supported". Where another of this author's components needs to do something to a Navidrome track
that only this repo can do correctly, the pattern is: expose a small `service_base`-derived
interface here (GUID + pure-virtual contract only, `FB2K_MAKE_SERVICE_INTERFACE_ENTRYPOINT`,
implementation in `NavidromeServices.cpp` or a dedicated `.cpp`), and the other component vendors a copy of
just the contract header (GUID must match byte-for-byte) and finds it via
`service_enum_t<T>` at runtime. No build-time coupling, no-op if the other component isn't
installed.

- **`navidrome_rating_api`** (`NavidromeRatingService.h`) — lets another component set a rating
  on a navidrome:// track (`set_rating_async`, preserves starred state, syncs the change back to
  matching playlist entries) without hitting the tag-write error above. First (only) consumer:
  [foo_ui_panels](https://github.com/santiagorod92/foo_ui_panels) — its star-rating widgets
  (`src/core/skin_engine.cpp`'s `set_rating()`/`TAG:SET:rating:`) route through this service instead
  of the standard file-tag path when the track is one of ours; its rating *display* also reads
  `NAVIDROME_RATING` as a fallback field (see this repo's own "Don't name an exported field
  `rating`" gotcha below — that's exactly why a separate read path is needed on the consumer side
  too). Vendored copy: `foo_ui_panels/src/core/navidrome_rating_api.h`.

- **`navidrome_library_api`** (`NavidromeLibraryService.h`, both platforms: service in `NavidromeServices.cpp` over
  the seams in `NavidromeLibraryPlatform.h` — `libraryCore`/`libraryClient`/`libraryFetchCover`,
  defined in `src/platform/win/NavidromeLibraryServiceWin.cpp` and `src/platform/mac/MacSubsonicBrowserClient.mm`;
  album walk = shared `listLibraryAlbums()`, tested in `tests/LibraryServiceTests.cpp`) — publishes the server's albums (streamed through a caller-implemented
  `library_album_sink`, plain `const char*`/`int` so nothing crosses the DLL boundary in a
  std/pfc container), cover-art bytes (`fetch_cover`, thumbnails cached under `<id>@<size>`) and a
  `play_album` action. `list_albums`/`fetch_cover` block (one request per artist) — worker thread
  only. Consumer: foo_ui_panels' album grid (`src/panels/album_list.cpp`). Vendored copy:
  `foo_ui_panels/src/core/navidrome_library_api.h`.

- **`navidrome_lyrics_api`** (`NavidromeLyricsService.h`, both platforms: service in `NavidromeServices.cpp` over
  `navidrome::lyricsForTrackURI()` + `libraryClient()`) — a navidrome:// track's lyrics, streamed
  line by line through a caller-implemented `lyrics_sink` (`on_begin(synced, count)` then
  `on_line(startMs, text)`, `startMs` = -1 when unsynced). `get_lyrics` blocks on a cache miss, so call it from a
  worker thread only. Shares the session `lyricsCache()` with the macOS lyrics panel. Consumer:
  foo_ui_panels' `lyrics_panel` (vendored copy: `foo_ui_panels/src/core/navidrome_lyrics_api.h`).

Adding a new cross-component interface: follow the same shape, and add a bullet here naming the
interface, what it's for, and every known consumer — keeps both repos' CLAUDE.md honest about
who depends on what without needing to grep across machines.

## Shared conventions (foo_ui_panels ⇄ foo_navidrome)

foo_ui_panels (Panels UI) and foo_navidrome are sister components, sibling checkouts under one
parent (`../foo_ui_panels`, `../foo_navidrome`). They're developed together, installed together
and tested in the same foobar2000. **This section is identical in both repos' CLAUDE.md** and
holds only what's true for both; anything repo-specific stays in the repo's own sections.
- **Editing it:** change both copies in the same round, keep the subsection order below, one
  terse bullet per fact (`**Topic:** fact`), no narrative or session logs. Check they match:
  `diff <(awk '/^## Shared conventions/{f=1} /^## /&&!/^## Shared/{f=0} f' ../foo_ui_panels/CLAUDE.md) <(awk '/^## Shared conventions/{f=1} /^## /&&!/^## Shared/{f=0} f' ../foo_navidrome/CLAUDE.md)`.
- **What goes here:** a rule, tool, layout or gotcha that's useful in both repos (SDK, build
  layout, versioning, logging, release, test environments, troubleshooting). If it's useful in
  only one repo, it goes in that repo's own sections.

### How they work together
- **Contracts:** foo_navidrome publishes `service_base` interfaces, and foo_ui_panels vendors a
  GUID-matched copy of the contract header and finds it with `service_enum_t` at runtime. There's
  no build coupling, and the feature is a no-op when the other component is missing. foo_navidrome's
  "Cross-compatibility with other same-author components" section is the full list: each
  interface, its consumers and its vendored copies.
- **Current links:** `navidrome_rating_api` drives Panels UI's star ratings on `navidrome://`
  tracks, which also read the `NAVIDROME_RATING` field. `navidrome_library_api` feeds the
  Panels UI album grid (`album_list`) and `library_tree`. `navidrome_lyrics_api` feeds Panels
  UI's `lyrics_panel`.
- **Changing a contract:** a change to a contract header (GUID, vtable order, sink signatures)
  lands in both repos in the same round, and the vendored copy stays byte-identical to the
  original. A new interface also gets a bullet in foo_navidrome's cross-compatibility list.
- **Runtime check:** test a feature that crosses the boundary with both DLLs installed (Wine,
  macOS VM). Also check that each side still works with the other component missing:
  `ui-test.sh <platform> solo` in either repo moves the other component out of the profile for
  the run (restored after) and runs that repo's smoke steps.

### SDK
- **Source:** `reupen/foobar2000-sdk-unmodified`, tags `SDK-YYYY-MM-DD`. Don't use the
  `marc2k3` or `razielanarki` mirrors: they're stale and missing `helpers-mac/`.
- **Location:** one checkout, shared by both repos: `../foobar2000/{SDK,helpers,helpers-mac,shared,
  foobar2000_component_client}` + `../pfc`. A bump therefore affects both repos at once. CI
  re-clones upstream's default branch on every run.
- **In use: SDK-2026-10-01.** foobar2000 v2.26; C++20 is required (since 2026-09-16).
- **Bump procedure:**
  1. Clone the tag into a scratch dir.
  2. Run `diff -rq` against the sibling SDK folders.
  3. Read foobar2000.org/changelog-sdk.
  4. `git grep` both repos for every symbol the diff touches.
  5. Copy the changed files into the siblings.
  6. Build every leg of both repos and run both test suites.
  7. Update the version in "In use" above (both copies) and in each README's development table.
- **Sync history:**
  - 2026-09-16: C++20 is required. pfc now redirects to `shared.dll` through
    `wrap_pfc_hooks.h`, and the ARM64EC link needed the hooks. `skipTrack.h` was added.
  - 2026-10-01: pfc's ARM64EC `/alternatename` is fixed (`#` names). `now_playing_album_art_notify`
    may now pass null data.
- **Upstream breakage:** a sync can break a build with no change on our side (a renamed
  target, a new required integration step). Diff the live upstream files and read the SDK
  changelog before debugging our code.

### Build, version, release
- **Toolchain:** local Windows builds are done on Linux with clang-cl + lld-link + xwin (splat
  `--arch x86,x86_64,aarch64`), static `/MT` CRT, x64 + x86. Release builds also include ARM64EC:
  foo_ui_panels builds it with clang-cl, foo_navidrome with MSBuild in CI. macOS ships as a
  universal bundle, and the x86_64 slice must stay (the VM guest is Intel).
- **Version:** `scripts/version.sh` is the same resolver in both repos: env override
  (`PUI_VERSION` / `NAVIDROME_VERSION`) → `git describe` against `v*` → `version.txt`
  (`export-subst`). No version is kept by hand. CI checks out with `fetch-depth: 0`. Run
  `git fetch --tags` after each release.
- **Release:** semantic-release with Conventional Commits (`feat` = minor;
  `fix`/`perf`/`refactor` = patch; `chore`/`docs`/`ci`/`style`/`test` = no release). `main`
  is protected (PRs only) and nothing is committed back. `CHANGELOG.md` is kept by hand in the
  release PR. `notify-n8n` publishes to foobar2000.org. If the head commit is non-releasing,
  dispatch the workflow by hand.
- **Release asset:** one `<component>_<version>.fb2k-component` per release, labelled
  `<component> <version> (macOS + Windows x86/x64/ARM64)`. Every place that uploads it
  (`.releaserc.json`, any `gh release upload --clobber` re-upload) uses that same label.
- **Commits:** author Santiago Rodriguez only, no AI trailers. Push only at the end of an
  iteration.
- **CI path filters:** files that aren't part of the component don't trigger CI builds:
  `**.md`, issue forms, `LICENSE`, `.gitignore`, and local-only dev/test scripts and tools. The
  `paths-ignore` lists live in foo_ui_panels' `build.yml` (push + PR; a new PR push cancels the
  superseded run) and in foo_navidrome's `release.yml` (push). A new local-only script or tool
  is added to that list in the same change. Anything CI builds, tests or packages with stays off
  it. A release-worthy commit that only touches ignored paths doesn't release; dispatch the
  workflow by hand.

### Code style and working rules
- **Cross-platform:** every feature or fix lands on Windows and macOS. Logic goes in shared,
  SDK-free code covered by unit tests; only the wiring is per-platform.
- **No code comments:** none in `src/`, `tests/`, `scripts/`, `tools/`, the `Makefile` or the
  workflows. The *why* goes in CLAUDE.md or the commit message.
- **README:** every user-visible change updates the README in the same change.
- **Make targets:** a command run more than once, or with easy-to-forget flags, becomes a

### Logging and diagnostics
- **Log file:** `<profile>/<component>.log` (`foo_ui_panels.log`, `foo_navidrome.log`). Shape:
  - WARN+ by default; INFO when the component's verbose toggle is on.
  - Rotates to `.1` past 2 MB.
  - Each session opens with an always-written NOTE banner (component, foobar2000, OS, arch,
    Wine versions).
  - Lines from before the log path is known are buffered.
- **Copy Diagnostics:** an in-memory ring of recent lines feeds the Copy Diagnostics report in
  Preferences, on both platforms. The text is pasted into public issues, so it is always
  redacted: home → `~`, user name, server host, auth/URLs (`scrubAuth`). Issue forms live in
  `.github/ISSUE_TEMPLATE/`.
- **Keep the logging matched:** a new logging or diagnostics feature (level, field, redaction,
  rotation) is mirrored in the other repo unless there's a stated reason not to.

### Test environments
- **Wine:** `~/.foobar2000` (fb2k v2.26 x64), with both components in
  `profile/user-components-x64/<name>/`. Each repo's `win-build`/`deploy` installs its own DLL,
  and the other stays as last installed. `tools/wclick.c` (originally from foo_ui_panels) posts
  clicks and keys without touching the host pointer.
- **macOS VM:** `../macos-devbox` (`mvm`, dockur/macos, Intel guest). **Windows 11 VM:**
  `../windows-devbox` (`wvm`, dockur/windows), for Dark Mode, DPI and native theming that Wine
  fakes. Never `docker prune`/`rm`/`rmi`.
- **UI tests:** both repos drive the real foobar2000 with one script,
  `scripts/ui-test.sh <wine|win11|mac> <scenario>`: each scenario is written once over a small
  per-platform driver and asserts on the component log, the process and crash reports.
  `ui-test.sh compare <scenario> [platforms]` prints a step matrix that marks where platforms
  differ (`PARALLEL=1` runs them at once; one test agent per platform works the same way).
  Run Windows changes on Wine *and* the Win11 VM: Wine is an emulation and real Windows
  differs (dark-mode theming, popups, focus). Check the screenshots, not only the log.

### Troubleshooting
- **DLL fails to load** ("No access to memory location"; fb2k falls back to the Default UI):
  usually a foobar2000 object created at static init. Create it lazily.
- **Is the DLL loaded under Wine?** `grep -i foo_ /proc/$(pgrep -f 'foobar2000[.]exe')/maps`.
  Check the component log for a new session banner.
- **`pkill -f`/`pgrep -f`:** a pattern that also appears in your own command line kills your
  shell. Use `'foobar2000[.]exe'`.
- **No debugger:** logging is the diagnostic channel. Add log lines at decision points instead
  of guessing.
- **Build breaks right after an SDK sync:** see SDK › "Upstream breakage" before touching our
  code.

## Architecture

Shared C++ core + per-platform UI/HTTP layers, laid out like foo_ui_panels:

```
src/core/            shared by both platforms: SDK-free logic + SDK glue (main.cpp + one .cpp per topic) + stdafx.h prefix header
                     + cross-component service contracts. Anything a platform could share goes here.
src/platform/mac/    macOS only: ObjC++ transport/settings adapters, service registration, AppKit UI
src/platform/win/    Windows only: WinHTTP/ATL adapters, registration, Win32 UI, foo_navidrome.vcxproj
third_party/wtl/     vendored WTL headers (Windows builds; CI wires it via Directory.Build.targets)
third_party/columns_ui-sdk/  vendored Columns UI SDK (0BSD): the CUI panel's uie::window contract
tests/               SDK-free unit tests over src/core
```
Includes are relative, foo_ui_panels-style: platform files use `"../../core/X.h"`, tests use `"../src/core/X.h"`, siblings in the same folder use bare names. `version_generated.h` stays at the repo root (every toolchain has the repo root on its include path: Xcode `$(SRCROOT)`, vcxproj `../../..`, clang-cl `-I $REPO`). The Xcode project/workspace stay at the repo root (the workspace's `../SDK/...` refs assume it); their groups point into `src/`. File bullets below use bare names — `src/core/` unless the name says otherwise:

- `main.cpp`, `stdafx.h`, `SubsonicTypes.h` (+ its topic headers, below) — cross-platform shared code (`main.cpp` = component version, advconfig switches, log init, Copy Diagnostics, `warnAuthRejectedOnce()`; pure-C++ data types, `trackIdFromURI()`, `StarKind`/`AlbumListType` enums)
- The SDK glue that used to live in `main.cpp` is one `.cpp` per topic, each implementing the header of the same name: `NavidromePlaylistSync.cpp` (rating push-back, `scanPlaylistAlbums()`, `collectActivePlaylistIds()`), `NavidromeTrackInput.cpp`, `NavidromeBrowserEnqueue.cpp` (plus `makeTrackHandles`/`playFrom`/`reportError`, declared in the internal `NavidromeSdkGlue.h` because AudioMuse and the play queue reuse them), `NavidromeAudioMuse.cpp`, `NavidromePlayQueue.cpp`, `NavidromeMenus.cpp` (playlist context menu + File › Open Navidrome Browser / Bookmark Current Position), `NavidromeServices.cpp` (the three cross-component services), `NavidromeScrobbler.cpp` (scrobbler, startup rating refresh, `setRatingOnServer`/`setStarredOnServer`), `NavidromeInput.cpp` (the `input_singletrack` handler + `fb2k::skipTrack`), `NavidromeArtExtractor.cpp` (`album_art_extractor` over `libraryFetchCover`), `NavidromeSettings.h/.cpp` (every shared `cfg_*` var; include the header instead of an `extern` block). A new SDK `.cpp` in `src/core/` needs a `vcxproj` `ClCompile` (default PCH) and four `project.pbxproj` entries in the `core` group.
- `I18n.h/.cpp` + `I18nSpanish.cpp` — UI translation, SDK-free. English text is the key: `tr("Refresh")` returns the Spanish entry or the English itself; `trf("Added {0} tracks", {n})` substitutes `{0}`..`{9}` after translating; `N_("…")` marks a key used indirectly (static tables, constants) so `scripts/i18n-check.py` sees it. The language is resolved once, on the first `tr()`, through the resolver `main.cpp` installs at static init (`cfg_ui_language` "" = system, `systemLanguageCode()` seam: Win `GetUserDefaultUILanguage`, Mac `NSLocale.preferredLanguages`); `languageOptions()` feeds both prefs pages' Language control. Tested in `tests/I18nTests.cpp` (placeholders must match between key and translation). Platform wrappers: `trw`/`trfw` (`WinUi.h`), `NDTr`/`NDTrf`/`NDStd` (`src/platform/mac/MacI18n.h`).
- `NavidromeGuids.h` — the one GUID table (`navidrome::guids::*`, `make(group, item)`), every platform included. Read it before picking a new tail. `mainmenuBookmark` and `macUiElementBrowser` share `0x01,0x0e` on purpose: different service classes, and changing either loses users' keyboard shortcuts or Mac layouts.
- `NavidromeLibraryPlatform.h` — the platform seams the SDK glue calls: `libraryCore()` (the `SubsonicCore` singleton), `libraryClient()` (an `IBrowserClient`), `libraryFetchCover()` (cached cover bytes), `showBrowserWindow()`. Windows implements them in `NavidromeLibraryServiceWin.cpp`/`BrowserWindow.cpp`, macOS in `MacSubsonicBrowserClient.mm`/`NavidromeBrowserController.mm`.
- `CoreBrowserClient.h` — header-only `IBrowserClient` over `SubsonicCore&` (hidden categories via a callback). Both platforms use it; there's no per-platform browser adapter any more. Unit-tested (`tests/CoreBrowserClientTests.cpp`).
- `SubsonicCore.h/.cpp` — shared Subsonic API core, SDK-free. Owns every request body: URL/auth assembly, retry loop, status-wrapper check, JSON→`navidrome::parseX`, music-folder cache, multi-library fan-out. Platform fills two seams: `IHttpTransport::getOnce()` (one GET, no retry) and `ISettingsProvider::load()`. Unit-tested (`testSubsonicCore`).
- `SubsonicClient.h/.mm` — macOS adapter over `SubsonicCore`: `MacHttpTransport` (NSURLSession, each GET in an `@autoreleasepool` because core calls come from plain `std::thread`s) + `MacSettingsProvider`, `NavidromeSendSync()` (the one semaphore-wrapped data task), raw byte paths for cover art/download, and ObjC `Subsonic*` wrappers only for what the AppKit prefs/actions still bind to (playlists, music folders, radio stations). Reach anything else through `[client core]` or `navidrome::libraryCore()`, not a new ObjC method.
- `src/platform/win/SubsonicClientWin.h/.cpp` — Windows adapter over `SubsonicCore`: `WinHttpTransport` (WinHTTP) + `WinSettingsProvider`, plus Windows-only `httpGetBinary`/`httpDownloadToFile`. Singleton facade forwarding to `m_core` (`core()` exposes it). Every WinHTTP request goes through `src/platform/win/WinHttpClient.h/.cpp` (`openWinHttpRequest` → `sendWinHttpRequest` → `winHttpStatus`/`readWinHttpBody`; crack/open/connect/headers live there once).
- `NavidromePlugin.mm` — macOS registration: main prefs page, `library_viewer` factory, Media Library page, the two `ui_element_mac`s. Each other prefs page is its own controller + page factory: `NavidromeRadioPrefsController.mm`, `NavidromeLibrariesPrefsController.mm`, `NavidromeBrowserSectionsPrefsController.mm`, `NavidromeAudioMusePrefsController.mm` (mirrors the Windows `*PrefsWin.cpp` files).
- `NavidromeInput.cpp` — `input_singletrack` handler for `navidrome://track/<id>?...` URIs, one implementation for both platforms: `get_info` = `navidrome::applyTrackInfo()`, decoding = `navidrome::TrackDecoder` (both in `NavidromeTrackInput.h/.cpp`). Metadata embedded in URI; HTTP stream URL resolved at decode time through `libraryCore().streamURL()`. Registered `input_entry::flag_redirect`, opens nested decoder via `g_open_for_decoding(fromRedirect=true)`. Also the `fb2k::skipTrack` implementation (SDK 2.26+) — see Decisions.
- `NavidromeTrackInput.h/.cpp` — the shared input half. `applyTrackInfo(TrackURI, file_info&)` writes every meta field, length, codec, rating/starred and ReplayGain; it's also what `makeTrackHandles` uses for the enqueue-time hint, so `get_info` and the hint can't drift apart. `TrackDecoder` opens the stream (custom headers, decoder hint, broken-track marking) and seeks, reopening at `timeOffset` when the stream can't seek (see Decisions).
- `SubsonicTypes.h` — umbrella over the SDK-free topic headers, which every consumer still reaches through it: `SubsonicModels.h` (API data types, `StarKind`/`AlbumListType`, `ServerInfo` + OpenSubsonic extensions, `PlayQueue`), `TrackTags.h` (`TrackTags`/`ReplayGain` carried by `Song`, `BrowserNode` and `TrackURI`; `sanitizeReplayGain`, `trackTagMetaFields`), `SubsonicErrors.h` (`ErrorKind`/`Error`, `navidrome::retry`), `TrackUri.h` (URI codec `TrackURI`/`buildTrackURI`/`parseTrackURI`, percent-encode/decode, `resolveArtId`/`rawQueryParam`, `sanitizeFileName`), `LibraryFilter.h` (multi-library fan-out helpers), `Json.h` (`json::Value`/`json::parse()`), `SubsonicParsers.h` (Subsonic mappers `parseSong`/`parseAlbum`/…, lyrics parsers + `lyricsCache()`, `parseSubsonicResponse()`). The umbrella itself keeps the small leftovers: stream/transcode options, `scrobbleSubmitThreshold()`, header-line parsing, `ScrobbleTracker`, `BrokenTrackRegistry`/`brokenTrackRegistry()` (session-scoped dead-track set backing `skipTrack`), `SessionEnv`. Put a new SDK-free helper in the topic header it belongs to (or a new one, `#include`d from the umbrella in dependency order), not in the umbrella.
- `NavidromePlaylistSync.h/.cpp` — `syncRatingsToPlaylists()` pushes `NAVIDROME_RATING`/`NAVIDROME_STARRED` onto playlist entries via forced hints. `scanPlaylistAlbums()` collects `albumId=` values for startup refresh.
- `NavidromeBrowserModel.h/.cpp` — shared browser tree logic, SDK-free. Owns `navidrome::BrowserNode`, category order, model→node mappers, row-display formatting, and (behind `IBrowserClient`) `buildRootNodes()`, `fetchChildren()`, `collectSongsDeep()`, star/rate mutation, Instant Mix/Random Mix/Artist Info fetch, `syncBrowserNodesToPlaylists()`. Both platforms use `CoreBrowserClient` as the `IBrowserClient`. Also owns the small UI texts both views print (`rootLoadSummary`, `downloadFileName`/`downloadSummary`, `sentPlaylistSummary`) and `searchSongNodes()` with `kMinSearchQueryLength`. Unit-tested (`testBrowserModel`, `testBrowserFetchDispatch`, `testStarRatingSimilarRandom`).

### Windows testing on an Apple Silicon Mac — `make win11-arm*` (`scripts/win11-arm.sh`)
Same commands as the Linux Win11 VM below (`make win11-arm` starts it and opens its screen in a browser tab, `-web`/`-up`/`-down`/`-ssh`/`-logs`/`-status`/`-shot`/`-reset`), but the VM is **QEMU with Apple's hypervisor (HVF)**, not a dockur container. Tried first and dropped (2026-10-17): `dockurr/windows-arm` in a colima profile with nested virtualization (M3+, macOS 15+) gets KVM, but Windows hangs at "Start boot option" with one vCPU at 100% (Apple's nested virtualization only carries Linux guests), and without KVM it's emulated and far too slow. dockur is still used once, by `win11-arm.sh prepare` (`-up` runs it when the files are missing): `dockurr/windows-arm` with `KVM=N` in the default colima profile runs until "Booting Windows", i.e. until it has downloaded the Windows 11 ARM ISO from Microsoft and built its tested unattended setup image (`setup.img`: user tester/tester, the virtio ARM64 drivers in `$WinPEDriver$`, our `dev/win11-arm/oem/install.bat` that enables OpenSSH); then the ISO, `setup.img` and dockur's noVNC client are copied to `~/.local/share/foo_navidrome-win11-arm/` and the container and its volume are removed. `up` replicates dockur's QEMU device layout (virtio-scsi disk `data.img`, ISO and `setup.img` as USB storage, ramfb, xhci + kbd/tablet) with `-accel hvf`, user-mode networking (`127.0.0.1:2223`→22, `:3390`→3389), VNC with a websocket on `:5705`, and a `python3 -m http.server` serving noVNC on `127.0.0.1:8006`; both run as launchd jobs (`com.foo_navidrome.win11-arm.vm`/`.web`, `launchctl submit`) so the VM survives closing the terminal or the editor (a colima started from a terminal died with the editor session, `SIGTERM` mid-install). Traps found on the way:
- **Firmware: Homebrew QEMU's `edk2-aarch64-code.fd`, not dockur's `windows.rom`.** With dockur's firmware the Windows boot manager hangs at "Start boot option" under HVF too; with Homebrew's it boots. `-fw_cfg name=opt/org.tianocore/UninstallMemAttrProtocol,string=y` (from dockur's command line) is kept: recent edk2's memory-attribute protocol is a known Windows-ARM boot hang.
- **"Press any key to boot from CD"** times out on a headless boot, so `up` sends Enter through the QEMU monitor (`monitor.sock`) for the first 20 s only, and only when it has just created the disk (an installed system boots from the disk first, but Enter at the wrong moment there is still a stray key): longer and it lands on Windows Setup's focused *Cancel* button ("Are you sure you want to quit?", dismissed with `sendkey n`).
- **The noVNC URL needs `path=` (empty).** dockur's noVNC defaults to `websockify` (its nginx proxies that), and QEMU's built-in VNC websocket answers 404 on any path but `/`; the page then just retries. Its polls for `msg.html` 404 too, which is harmless (that page is dockur's status overlay).
- `make win11-arm-shot` screendumps through the same monitor socket (no VNC client needed); that's how the hang above was told apart from a slow boot.
- **macOS Local Network privacy blocks QEMU from the LAN.** A launchd job running a non-Apple binary gets no permission prompt and is silently denied (`No route to host`) on private addresses, while the internet works; Apple binaries (`/usr/bin/nc`, `curl`) aren't blocked, even when a non-Apple process spawns them. A Navidrome on the LAN is therefore reached through a slirp `guestfwd`: `up` reads the server URL from `SEED_CONFIG`, and when it resolves to a private address adds `guestfwd=tcp:10.0.2.100:<port>-cmd:/usr/bin/nc <ip> <port>`; `seed` points the guest's `hosts` file at `10.0.2.100`, so TLS still sees the real hostname. A new server address needs `down` + `up`.
- **After the install:** `provision` (ssh key via `expect` with the tester password, a firewall rule, then the foobar2000 ARM installer with `/S`), `seed` (our `cfg_var` rows + `foo_navidrome.*` from the Mac profile, like `win11-seed`), `deploy` (DLL into `user-components-arm64ec/foo_navidrome/`, foobar2000 restarted). `fb2k start|stop|cmd|log` runs in the desktop session through a one-off `LogonType Interactive` scheduled task, like `wvm`; `stop` is `foobar2000 /exit` first (a killed foobar2000 asks for safe mode on the next start), and `cfg "<SQL>"` edits `config.sqlite` with foobar2000 stopped. PowerShell goes over ssh as `-EncodedCommand` (nested quoting through ssh and cmd.exe breaks otherwise) with `$ProgressPreference` off (the progress stream comes out as CLIXML). The verbose-log advconfig is stored as `advconfig.unnamed.<GUID>` in `configInts` (`fb2k::advconfig_autoName`).
- **Driving the UI:** keys go through the monitor (`sendkey`) to the foreground window. A window opened through the scheduled task doesn't take focus until it gets a click, and the monitor's `mouse_move` is relative with pointer acceleration, so clicks can't be aimed: one click anywhere in the window gives it focus, then everything is keyboard. The context-menu key is `shift-f10` (`sendkey menu` doesn't reach Windows as `VK_APPS`). A Win32 menu item without a mnemonic is picked by its first letter, but foobar2000's own items have mnemonics (*Co**n**vert*), so arrows are safer there.
- `make win11-arm-test` (`run-unit-tests.sh win11-arm`) builds the unit tests with the Mac's clang-cl (`/MT`, `/Tp`) and runs them in the guest, which is how the `_WIN32`-only branches run (e.g. deleting a file another handle holds open).
The DLL is cross-compiled on the Mac with `make win-build-mac` (`scripts/win-build-mac.sh` + `win-build-mac-cc1.sh`, clang-cl/lld/xwin from `make win-setup-toolchain-mac`) into `build-win-mac/foo_navidrome.dll`: x64 only (clang can't build ARM64EC; CI does), which foobar2000 on Windows ARM runs emulated — fine for UI testing.

### Versioning + dev loop
One resolver: `scripts/version.sh` → `version_generated.h` (gitignored) → `DECLARE_COMPONENT_VERSION`, i.e. what foobar2000 shows under *Preferences › Components* (read from the binary at load — nothing to update inside foobar, just swap the DLL/bundle and restart). Order: `$NAVIDROME_VERSION` (releases pass semantic-release's version — the tag doesn't exist yet while they build; an explicit `--patch/--minor/--major` bump too) → `git describe` against the last `v*` tag (`1.21.2` on a clean tag, `1.21.2-dev.3+2a46400[.dirty]` after it) → `version.txt`, only read in a tree without `.git`: in the repo it's a `$Format:%(describe…)$` placeholder that `git archive` (GitHub source zips) expands (`.gitattributes` `export-subst`), so no version number is ever maintained by hand — releases are the `v*` tags. Every build path calls it: `win-build-local.sh`, `win-build-mac.sh`, Xcode's "Generate Version Header" phase, `mac-dev-build.sh`/`mac-ci-build.sh` (as the `NAVIDROME_VERSION` build setting), `mac-vm-build.sh` (resolved on the host: the guest copy and `mac-dev-build.sh`'s SDK-tree copy have no `.git`), `build-windows.yml` (`fetch-depth: 0` so dispatch builds see tags). **Run `git fetch --tags` after a release merges** or local builds describe against the previous tag. Check what a guest actually loaded: `make win11-ui ARGS='prefs components'`.
```bash
./scripts/mac-dev-build.sh                # build, install (no bump)
./scripts/mac-dev-build.sh --patch/--minor/--major/--no-install/--new-release   # bump = last tag + 1; --new-release needs one
```
`win-build-local.sh` mirrors this (same bump flags, default no bump). A bump counts from the last release tag (`version.sh --base`) and is only stamped, never written to the tree. Symmetric `make {win,mac}-build-{patch,minor,major}` targets.

### Release pipeline
`.github/workflows/release.yml` on push to `main`, via [semantic-release](https://semantic-release.gitbook.io/) reading [Conventional Commits](https://www.conventionalcommits.org/) (config `.releaserc.json`):
- `feat:` → minor · `fix:`/`perf:`/`refactor:` → patch · `chore:`/`docs:`/`style:`/`test:`/`ci:` → no release · `!`/breaking footer → major.
- **`commit-analyzer` and `release-notes-generator` type lists must stay in sync** — the `conventionalcommits` preset hides `refactor`/`docs`/`build` by default; any type added to `releaseRules` with `release != false` needs a matching non-hidden entry in `release-notes-generator`'s `presetConfig.types` or its notes are empty.
- Jobs: `version` (`semantic-release --dry-run`; exec's `verifyReleaseCmd` exports `next_version`) → in parallel `build-windows` (reusable `build-windows.yml`: one MSBuild job per arch — x64 / ARM64EC / Win32 matrix, unit tests on the x64 leg — then a Linux `package` job zips the Windows-only component, all stamped with that version) and `build-mac` (`make mac-test` + `mac-ci-build.sh <next_version>`, artifact `mac-component`) → `release` (Linux: semantic-release for real; its prepare step `scripts/release-package.sh` merges the mac component + Windows DLLs into the one asset, and fails if the mac build isn't stamped with the real next version) → `notify-n8n`. Nothing is published unless both platforms built.
- Plugin chain: `commit-analyzer` → `release-notes-generator` → `exec` (`release-package.sh <version>`, merges the prebuilt mac + Windows builds into the `.fb2k-component`) → `github` (tag + release + asset; notes = changelog). **`main` is branch-protected (PRs only)**, so no `git`/`changelog` plugins: nothing is committed back — nothing to keep in sync in the repo: every build derives its version from the tags (see Versioning), `CHANGELOG.md` is kept by hand: add the next version's entry inside the release PR itself (heading `## [x.y.z](compare link) (date)` with the version the PR's commit type will produce), since semantic-release never commits it back; GitHub Releases still get the auto-generated notes.
- **Preparing a release (standing rule, asked for 2026-10-15): the CHANGELOG entry and the commits are part of the work, not an afterthought.**
  1. **CHANGELOG first-class.** Add the next version's entry at the top of `CHANGELOG.md` in the release branch: heading `## [x.y.z](compare link vPREV...vNEXT) (date)`, then `### Features`, `### Bug Fixes`, and (when there's internal work worth naming) `### Code Refactoring`, each bullet starting with a bold scope (`**windows:**`, `**macOS:**`, `**browser:**`…). Write for users: what changed, where it lives in the UI (menu paths, prefs pages), what they need to do (e.g. re-add tracks, re-toggle a switch), limits and server requirements, issue links. One bullet per user-visible change; nothing that only matters to us outside *Code Refactoring*. Check every user-visible item of the release against the README too.
  2. **One logical change per commit**, Conventional Commits, each with a body that says *why* (what was wrong or missing, the decision taken) — never "misc fixes". Split mixed work tree changes into separate commits even when it takes hunk-level staging; verify each intermediate commit still builds and passes `make test`. Fold in any open docs-only PR the release should carry (keep its author/message) and close it after the merge.
  3. **Order the commits for semantic-release**: the push's *top* commit type decides the release, so the highest-impact commit (`feat` > `fix`/`perf`/`refactor`) goes last; a trailing `docs:`/`chore:` commit skips the release. The CHANGELOG commit goes before it. If the PR is squash-merged, its title must carry that type.
  4. Before pushing: full test/smoke round on every platform (Wine, Win11, Mac VM), README + CLAUDE.md updated, version = what the top commit type will produce from the last `v*` tag.
- SDK cloned from `reupen/foobar2000-sdk-unmodified` into the sibling layout at CI time (see Shared conventions › SDK).
- **`release.yml` only checks the push's top commit type** — a `chore:` HEAD (or a PR squash-merged as `ci:`/`docs:`) skips release even with a `feat`/`fix` underneath it; dispatch the workflow by hand then.
- First-time setup needs a starting tag (`git tag v<x.y.z> && git push --tags`) or semantic-release treats next release as v1.0.0.

## Decisions & Constraints

- **Media Library integration is native via custom URI + `library_viewer`.** foobar's Music Folders only accepts filesystem paths — no SDK hook for a remote source. Two SDK extensions: `input_singletrack` for `navidrome://track/<id>?...` (metadata in URI so playlists render without a network round-trip; stream URL resolved at decode time so playlists survive credential rotation), and `library_viewer` registration.

- **Embedded browser: three mount points, one `NSViewController` class**, each mount creating a fresh instance (Cocoa requires one superview per NSView). Data sharing happens at the model layer (`SubsonicClient` singleton), not the VC.

- **Browser logic is shared C++; the platform layer is just the view.** `NavidromeBrowserModel.h/.cpp` + `NavidromeBrowserEnqueue.h` own tree model, category list, child fetch, deep-collect, row-label formatting, playlist rating push-back, star/rate mutation, Instant Mix/Random Mix, enqueue/seek. `BrowserWindow`/`NavidromeBrowserController` keep only widget wiring, theming, menus, threading, and their `IBrowserClient` adapter. Add browser behaviour to the shared core, not a platform file.
  - macOS keeps ObjC `NavidromeNode` as a thin view-model bridged via `+wrapCoreNode:`/`-coreNode`; `NavidromeNodeType`/`NavidromeCategoryKind` must stay declared in the same order as the C++ enums (bridged by cast).

- **"All Songs" is an enqueue-only node, and the Windows tree fakes multi-select.** Asked for on Hydrogenaudio (2026-10): no way to load a whole library on Windows except one artist at a time. `CatAllSongs` → `SubsonicCore::getAllSongs()`: empty-query `search3.view` paged by `songOffset` (Navidrome/OpenSubsonic treat `""` as match-all), fanned out per active library; stops on a short page *or* a page with no new ids (guards a server that ignores the offset). `navidrome::isLeaf()` is true for it on purpose — inserting tens of thousands of tree items stalls both views — so it's only reached via `collectSongsDeep` (Add/Play/Enter/double-click). Win32 `SysTreeView32` has no multi-select: `BrowserWindow` subclasses it (`SetWindowSubclass`) — Ctrl+click toggles `TVIS_SELECTED`, Shift+click/Shift+arrows select a range from `m_selAnchor`, any other caret change (`TVN_SELCHANGED`) collapses back to one; right-click inside the selection keeps it. `selectedNodes()` walks from `GetRootItem()` — `GetFirstVisibleItem()` is the top *on-screen* row and silently drops scrolled-off selections. macOS just uses `allowsMultipleSelection`. Both go through `collectSelectionSongs` (shared; ObjC twin on Mac) which de-dupes songs across selected roots but keeps repeats within one (server playlists can repeat a track). Don't `#include <windowsx.h>` for `GET_X_LPARAM` — its `SubclassWindow` macro breaks ATL.

- **Root categories can be hidden; the setting is a CSV of stable keys** ([issue #27](https://github.com/santiagorod92/foo_navidrome/issues/27)). `browserCategories()` (`NavidromeBrowserModel.h`) is the one table of root categories: kind, title, and the key written to config. `cfg_browser_hidden_categories` (GUID tail `0x01,0x16`) holds the hidden keys (`parseHiddenCategories`/`joinHiddenCategories`; unknown keys are dropped, so renaming a key un-hides it). Keys are stored instead of enum values because `CategoryKind` order is bridged to the ObjC enum and must stay put. `buildRootNodes` reads it through `IBrowserClient::hiddenCategories()` (default: none, so the test fake opts in), and artists/libraries can't be hidden. Prefs page **Browser Sections** (GUID tail `0x01,0x17`, child of the main page): Windows `BrowserSectionsPrefsWin.cpp` stages until Apply, and *Reset page* is enabled whenever anything is hidden, not only while changes are pending; macOS `NavidromeBrowserSectionsPrefsController` (`NavidromePlugin.mm`) writes on every click. Open browsers reload on change: Windows through `BrowserWindow::reloadAllOpen()` (a static list of live windows, filled in `OnCreate`/`OnDestroy`, which covers the standalone window, prefs page, DUI and CUI mounts), macOS through `NavidromeBrowserSectionsDidChangeNotification`. The UI smoke tests count root rows (`CATEGORY_ROWS`), so run them with nothing hidden.

- **Instant Mix rides on `getSimilarSongs2.view`; AudioMuse-AI's other features are a direct client** ([issue #16](https://github.com/santiagorod92/foo_navidrome/issues/16)). The AudioMuse-AI Navidrome plugin makes Navidrome answer `getSimilarSongs2` from AudioMuse, so Instant Mix needs no AudioMuse settings and falls back to last.fm on a server without the plugin. Text search (CLAP), the AI Instant Playlist and Song Alchemy aren't exposed through Subsonic, so they POST to the AudioMuse server (URL + optional Bearer API token + optional `server` name for a multi-server AudioMuse). AudioMuse `item_id`s are the media server's own song ids, but rows lack suffix/duration/album ids, so each is resolved with `getSong.view` (one request per id, skipped + counted when the server no longer has it). Results land in a NEW foobar playlist named after the query. Instant Mix (browser item, formerly "Play Similar", and the playlist context item share `runInstantMix` in `NavidromeAudioMuse.cpp`) fills ONE dedicated "Instant Mix" playlist, replaced each time — the issue's author listens from mixes, not static playlists, and an insert-into-the-active-playlist first version kept growing them. Seed song first (dropped from the answer via `withoutSongId`), then played; when the seed is the now-playing track playback isn't restarted: re-mixing from inside the mix keeps that entry and replaces the rest, re-mixing a track playing from another playlist relies on foobar locating the playing handle at index 0 of the new playing playlist (verified on Wine: "Next" continues into the mix). Not retried: the instant playlist is an LLM run (5-minute timeout, can cost money per call). **Instant Mix falls back to AudioMuse-AI directly** ([issue #26](https://github.com/santiagorod92/foo_navidrome/issues/26)) when `getSimilarSongs2` comes back empty (not on an error) and an AudioMuse URL is set: a one-item `/api/alchemy` ADD (`audiomuse::similarTo`, `Kind::InstantMix`) rather than AudioMuse's own `GET /api/similar_tracks`, so it reuses the POST-only `IJsonPoster` on both platforms; alchemy excludes the seed and samples with a temperature, fine for a mix. Song and artist seeds only (alchemy has no album type) — an album seed gets an explanatory message instead. The no-result texts are `audiomuse::noSimilarMessage()` (tested). A Navidrome without the AudioMuse plugin answers from last.fm, which is empty for less-played tracks: that was the issue. Everything runs under a modeless `threaded_process` (progress + Abort) from `NavidromeAudioMuse.cpp`. Song Alchemy is hidden until an AudioMuse URL is set (playlist menu: `context_get_display`; Win browser: menu build; Mac browser: `-menuNeedsUpdate:`). GUIDs: cfg `0x04,0x01-04`, prefs page `0x04,0x05`, main-menu group/cmds `0x04,0x10-12`, context items `0x03,0x10-11`.

- **The browse tree rebuilds itself when stale** (`kBrowserTreeMaxAgeMs` = 30 min, `browserTreeIsStale()`/`shouldReloadAfterEmptyCollect()` in `NavidromeBrowserModel.h`, tested in `BrowserFetchTests.cpp`). Nodes hold the server ids from load time and expanded nodes keep their children, so a browser left open across a Navidrome rescan queued nothing on Play/Add until a manual Refresh — `collectSongsDeep` dropped the fetch error. It now reports the first error (`std::string* error` out-param), and both views stamp their last successful root load: Windows' singleton window (hidden, not destroyed, on close) reloads on reopen when stale; on every mount a Play/Add that resolves zero songs reloads the tree when a fetch failed *or* the tree is stale, then shows "list reloaded, select again" (old nodes can't be mapped onto the new tree). Any Play/Add that comes up short (failed, partial, or zero tracks) also pops an error via `showBrowserQueueError()` (`NavidromeBrowserEnqueue.cpp`, `popup_message` + console) with text from the shared, tested `queueProblemMessage()`, which suggests Refresh and quotes the server error. A startup-only refresh wouldn't help: every mount already loads fresh when created; the failure is a long-running session. macOS standalone windows are a fresh VC per open, so only the self-heal applies there.

- **Track tags travel in the URI, like the rest of the metadata** (`TrackTags`, `TrackUri.h`). Query keys: `albumArtist`, `composer`, `genre` (repeated, one per value), `disc`, `bpm`, `mbid`, `rgTrackGain`/`rgAlbumGain`/`rgTrackPeak`/`rgAlbumPeak` (present only when known: a 0 dB gain is a real value). A track's URI therefore changes when it gains tags, so an entry enqueued before this exists alongside a re-added copy (a one-time dedup miss, same as the RFC-3986 encoder change). `musicBrainzId` on a Subsonic song is Navidrome's recording id, exported as `MUSICBRAINZ_TRACKID` (Picard's name for it). The song `comment` is deliberately not carried: some libraries keep whole lyrics there and it would bloat every URI.
  - **`sanitizeReplayGain` drops values the server sends for untagged files.** Navidrome 0.64 sends `"trackPeak": 0` when a file has no track peak, and older servers sent all four as `0`: a peak ≤ 0 is dropped, and a block whose gains are all 0 with no peak counts as no ReplayGain at all (otherwise every untagged track would get an explicit 0 dB and override foobar2000's *preamp without RG info*).
- **Seek in transcoded streams reopens the stream at `timeOffset`** (`TrackDecoder`, `NavidromeTrackInput.cpp`). A transcoded stream has no length, so foobar2000's HTTP reader can't seek it. When the nested decoder reports `!can_seek()`, `SubsonicCore::canSeekByTimeOffset()` decides: transcoding possible (`streamMayBeTranscoded`: anything but `raw` without a bitrate cap) **and** the server lists the `transcodeOffset` extension (from `capabilities()`). Then `seek(s)` reopens `stream.view?…&timeOffset=floor(s)` and trims the first `s - floor(s)` seconds of decoded audio, so the position foobar2000 believes in stays exact. A seekable stream always uses the decoder's own seek. Navidrome caches transcodes: the first play of a transcode is a live, unseekable stream, a replay is a cached file with Range support, so which path runs depends on the server's cache (the UI scenarios accept both, and `PLAYQUEUE_FORMAT=aac make win-ui ARGS=playqueue` usually forces the reopen path with a format not cached yet).
- **Play queue sync is two explicit File-menu commands, no automatic sync** (shared in `NavidromePlayQueue.cpp`, GUID tails `0x06,0x01`/`0x06,0x02`). Save takes the playing playlist + playing index + position (or the active playlist + focus item when stopped), drops non-Navidrome items and keeps at most `kPlayQueueMaxIds` (100) ids starting at the current one (`playQueueWindow`, backfilled from earlier tracks near the end): `savePlayQueue.view` takes every id in one GET, and Windows' URL path buffer is 4096 wchars. An empty save is refused locally (the server would clear the saved queue). Restore fills a dedicated *Navidrome Play Queue* playlist (replaced each time, like Instant Mix), plays the saved current track and resumes via `seekWhenReady`. The planning (`planPlayQueueSave`/`planPlayQueueRestore`/`playQueueSaveSummary`) is SDK-free and tested (`tests/PlayQueueTests.cpp`).

- **Enter in the browser tree replaces the active playlist; double-click/Add/Play still append.** `clearFirst` bool threaded through both platforms' enqueue chain, `true` only on the Enter/`NM_RETURN` path (clears the active playlist only, nothing else).

- **Auto-skip stale/deleted tracks via `fb2k::skipTrack` (new SDK 2.26 extension point, 2026-09-16 sync).** A stale playlist/shuffle/repeat/Random Mix loop that keeps hitting a Navidrome track since deleted server-side used to retry the doomed HTTP GET every time it came up. Now: `decode_initialize()` on both platforms catches `exception_io_not_found` specifically (not `exception_io_net`/`exception_io_timeout` — those are transient, must still retry) around `g_open_for_decoding`+`initialize()`, marks the id in `navidrome::brokenTrackRegistry()` (`SubsonicTypes.h`, mutex-guarded `unordered_set`, session-scoped — never cleared mid-run, matches every other session-only cache here), then rethrows so the existing error path is unchanged. Each platform's `NavidromeInput.mm`/`src/platform/win/NavidromeInputWin.cpp` also registers a `fb2k::skipTrack` implementation (`navidrome_skip_track`/`navidrome_skip_track_win`, `FB2K_SERVICE_FACTORY`) whose `testTrack()` is the core's preflight before it ever opens a track — a hit skips without attempting the decode at all. Registry logic is SDK-free and unit-tested (`testBrokenTrackRegistry`); the `fb2k::skipTrack`/`exception_io_not_found` wiring itself needs live playback to verify and is SDK-only, so it isn't (and can't be) covered by the `tests/` suite.
  - **Requires an SDK sibling with `skipTrack.h`** (SDK-2026-09-16 or newer).

- **Album art is a full `album_art_extractor`, not `album_art_fallback`** — guarantees `open()` is called, more reliable for streamed content. `is_our_path` matches `navidrome://` URIs and legacy `/rest/stream.view` URLs (old playlists). Art id priority: `coverArt=` → `id=` → `<id>` segment of the URI.

- **`.fb2k-component` multi-arch layout:** macOS bundle under `mac/`, Windows x86 at zip root, x64 under `x64/`, ARM64EC under `arm64ec/`. foobar prefers `arm64ec/` on ARM, falls back to x64 emulation. ARM target is ARM64EC (x64-ABI-compatible), not pure ARM64. Touching the arch set = update both workflows + the vcxproj's ProjectConfiguration list.

- Linux is intentionally unsupported (no foobar2000 Linux build).

- **Multi-library filter is client-side fan-out** ([issue #9](https://github.com/santiagorod92/foo_navidrome/issues/9)): Subsonic endpoints take one `musicFolderId`, never a list, so a subset selection = one request per selected id, merged+de-duped by item id. Shared kernels in `SubsonicTypes.h`: `appendMusicFolderParam`, `mergeFanOut<T>`. `getAlbum`/`getSong`, playlists, bookmarks, radio, `getSimilarSongs2` untouched (already id-scoped). **`getAlbumsForArtist` needs a second call:** `getArtist.view` ignores `musicFolderId` server-side, so when the filter is active it fans `search3.view` (which honours it) and filters via `filterAlbumsByArtistSearch()`; empty allow-set falls back to the unfiltered list + a `NAVIDROME_WARN` log. Whole decision funnels through `effectiveMusicFolderIds()` → `{}` means "one request, today's behaviour" (filter off, empty selection, `<2` server folders, or selection covers every folder). Config: `cfg_library_filter` (bool) + `cfg_library_ids` (csv), GUID tails `0x10`/`0x11`. Windows stages edits (Cancel discards); **Mac writes live on every click** (no apply/reset hook via `fb2k::wrapNSObject`) — true of every Mac prefs page in this component.
  - **A multi-library server groups the browser tree by library independent of the filter checkbox** — gate is `libraryGroupingIds()` (server has ≥2 libraries logic), not `activeMusicFolderIds()` (collapses to `{}` in fan-out-no-op cases where grouping must still happen). ≥2 grouping ids → one Library node per id, lazily expanded via `getArtistsForLibrary(id)`; artist nodes carry `libraryId` for scoped album fetch. Category nodes stay merged across libraries.

- **Windows theming has two independent axes** ([issue #4](https://github.com/santiagorod92/foo_navidrome/issues/4)): Dark Mode (native chrome, `fb2k::CCoreDarkModeHooks`, `m_darkMode.AddDialogWithControls(*this)` in `OnCreate`) and Colours/Fonts (`ui_config_manager::query_color`, works from a plain window per `CListControlFb2kColors`; `BrowserWindow::refreshThemeColors()` + `ui_colors_changed()` callback for live updates). Native push buttons can't be recolored (Win32 ignores `WM_CTLCOLORBTN` for `BS_PUSHBUTTON`). Any new top-level/embedded window needs both hookups.
  - **Every window of ours gets the Dark Mode hookup, prefs pages and popups included** ([issue #18](https://github.com/santiagorod92/foo_navidrome/issues/18), verified on real Windows 11 via `make win11-ui`). Three parts, all needed:
    1. **Every prefs page's `get_state()` ORs in `preferences_state::dark_mode_supported`.** Without it foobar2000 draws the *whole* Preferences dialog (tree, buttons, everything) light for as long as our page is shown, even in Dark Mode — that was the issue's "only this plugin's options are light".
    2. The four prefs pages, Custom Headers and both prompts each own a `fb2k::CCoreDarkModeHooks` and call `AddDialogWithControls(*this)` at the end of `OnCreate` (after every child exists — `AddControls` only walks the children present at call time).
    3. **`WM_ERASEBKGND` → `navidrome::win::eraseLikeDialog()`** (`WinUi.h`). Our pages are `CWindowImpl`s, not dialogs, so they paint their white class brush; asking for `WM_CTLCOLORDLG` like a dialog does gets the dark brush from the hooks. Without it: dark controls on a white page.
  - **Exception: a page holding a `SysListView32`** (Radio Stations, Libraries) uses `addDarkModeHooksKeepingLists()` (`BrowserWindow.cpp`): the core hook on a list view leaves it blank — on Wine *and* on real Windows 11 (where it also turned the page's buttons light) — so the list is skipped and themed by hand (colours + `DarkMode_Explorer`, header `DarkMode_ItemsView`) only when foobar is dark. `DarkMode_ItemsView` alone draws the header text dark grey on the dark header (unreadable, real Windows 11 only), so the list is subclassed (`darkListHeaderTextProc`) and the header's `NM_CUSTOMDRAW` sets the text colour. Wine reports Dark Mode as "not supported on this system", so the dark path is only checkable in the Win11 VM (`make win11-theme ARGS=dark`, then `make win11-ui ARGS='prefs radio'`).
- **Win32 layout is hand-built, so DPI scaling is ours to do** ([issue #18](https://github.com/santiagorod92/foo_navidrome/issues/18)). Write coordinates at 96 DPI and pass them through `navidrome::win::UiScale` (`src/platform/win/WinUi.h`, header-only); size anything holding text with `fitWidth()`/`textWidth()`/`lineHeight()` in the actual font, and take that font from `uiFont(*this)` (nearest ancestor's `WM_GETFONT`, i.e. the Preferences dialog's own font for a prefs page; stock GUI font otherwise). Hardcoded pixel rects with a DPI-scaled stock font is exactly what clipped every label/button at 150%. To test: `wine reg add 'HKCU\Control Panel\Desktop' /v LogPixels /t REG_DWORD /d 144 /f` with foobar closed, then **`wineserver -k`** when reverting (the server caches the DPI — a deleted value keeps scaling until it restarts). `foobar2000 -config` opens Preferences only on a cold start (not into a running instance under Wine), on `preferences.lastOpenPage`. wclick coordinates are DPI-virtualized at 144 (screen px ÷ 1.5).
- **The DLL builds with `/utf-8`** (`foo_navidrome.vcxproj` `AdditionalOptions`, and explicitly in both clang-cl scripts). Sources are UTF-8 without BOM; without the flag MSVC reads them as the ANSI code page and every non-ASCII wide literal (`L"Custom Headers…"`, `★`, `—`, `›`) ships as mojibake (`â€¦`) — invisible in the local clang-cl build, which assumes UTF-8 anyway, so it only ever showed up in CI/MSVC release builds (issue #18). Narrow literals happened to survive the round-trip, which is why only UI text broke.

- **UI translation keys are the English strings, and the language is fixed per session** (2026-10). A table keyed by English keeps the code readable (`tr("Refresh")` at the call site, no id constants) and makes a missing entry harmless (English shows). Composed messages became whole `trf` patterns with `{n}` placeholders, so word order and plurals can differ per language; the English output stayed byte-identical, which the existing message tests check. The language is resolved on the first `tr()` and never re-read: a change in Preferences says "restart foobar2000", because foobar2000 caches menu/prefs/UI-element names and half-translated windows are worse. Translated: windows, menus (main, context, browser), prefs pages and their names, UI element names, status lines, popups and console messages. Not translated: log lines and Copy Diagnostics (pasted into English bug reports), advconfig labels (their factories are built at static init, before the language is known), the component-version "about" text (same), product names. Translating menu names means `foobar2000 /command:<name>` uses the translated name; keyboard shortcuts are bound by GUID and keep working. Mac strings use curly quotes (`“{0}”`) and Windows straight ones, so both forms are keys.

## Gotchas

- **JSON responses are a real DOM (`navidrome::json`, `SubsonicTypes.h`) — walk the full path**, e.g. `root["searchResult3"]["album"].items()`. No substring key scanning (the old Windows scanner matched a key anywhere in the body, giving false hits through nesting levels). `.items()` unwraps Subsonic's single-element-array-collapsed-to-object. `checkResponse` returns Null on failure (`.isNull()`). Parser rejects trailing content after the top-level value.

- Every `SubsonicClient.h` model class needs a matching `@implementation` in `SubsonicClient.mm`, even if empty — an `@interface` alone compiles but fails at **link** time (`Undefined symbols ... _OBJC_CLASS_$_...`), not compile time.

- **`MediaEnrichmentLogic.cpp` / `EsLyricBridge.cpp` / `NavidromeBrowserModel.cpp` / `SubsonicCore.cpp` must stay `<PrecompiledHeader>NotUsing</PrecompiledHeader>`** in the vcxproj — the first three deliberately skip `stdafx.h` (kept SDK-free for standalone test builds); `EsLyricBridge.cpp` includes it but is still marked NotUsing.

- The unit-test host stubs `navidrome::syncRatingsToPlaylists` as a no-op (SDK-only, lives in `NavidromePlaylistSync.cpp`). A new shared-browser-core call into an SDK-glue-only symbol needs the same stub or an `IBrowserClient`-seam alternative.

- **Transcoding changes the codec — the decoder hint must follow.** Both input handlers pass the suffix through `navidrome::effectiveStreamSuffix()` before building the `track.<suffix>` hint (`"raw"`/`""` = original file, leave suffix alone).

- **`songIndexToRemove` is positional, evaluated per request** — send removals highest-index-first, or earlier removals shift later indices (silent wrong-track deletion at >50 removals, where chunking makes it worse).

- A `preferences_page`'s `get_parent_guid()` can point at another page's own GUID (not just an SDK branch GUID) to nest as a visible child — used by Radio Stations (parent = main Navidrome page's GUID, tail `0x05`).

- **Resume-from-bookmark needs a "seek when ready" poll** — `playback_seek()` can't be called right after `start()`. `navidrome::seekWhenReady()` (`NavidromeTrackInput.cpp`, both platforms, used by bookmarks and play-queue restore) ticks every 100 ms for ~3 s from a background thread, but **every `playback_control` call, `is_playing()`/`playback_can_seek()` included, runs on the main thread** through `fb2k::inMainThread`: calling them from the worker made foobar2000 2.26 die with a *Bug check* crash (found with the play-queue restore on Wine). Server positions (bookmark, play queue) are **ms**; `playback_control` is **seconds** — convert at the boundary.

- **Radio stations bypass the `navidrome://` scheme entirely** — raw `streamUrl` set directly as `playable_location_impl`, played by foobar's stock HTTP input. No custom headers reach a station stream; that's inherent to Subsonic radio, not a bug.

- `createInternetRadioStation.view` never echoes the new id back — both clients always return `""` on success; callers must check the error output, not treat empty-return as failure.

- **Lyrics lookup: by id, then a sticky per-server fallback.** `SubsonicCore::getLyrics` first asks `capabilities()` (below): when the server's extension list is known and lacks `songLyrics` (or it is plain Subsonic), it goes straight to legacy `getLyrics.view`. Otherwise it tries `getLyricsBySongId.view` (OpenSubsonic). Only an **HTTP 404** marks the server as lacking the endpoint: it's remembered per `serverUrl`, so a server switch re-probes. After that, every call goes to legacy `getLyrics.view?artist=&title=`, with artist/title read from the URI, and that path is skipped when either is empty. Any other by-id failure, including Subsonic code 70, is a plain error with no fallback. This mirrors the ESLyric searcher script's logic. Structured `offset` is *subtracted* from each line `start`. `lyricsCache()` caches "no lyrics" too, but never a failure.
- **Optional endpoints are gated on `SubsonicCore::capabilities()`, not discovered by error.** `serverInfo()` = `ping.view` (+ `getOpenSubsonicExtensions.view` when `openSubsonic` is true) → `ServerInfo` with `extensions` + `extensionsKnown`; `capabilities()` caches it per server URL for the session (a server switch re-probes; a failed probe caches nothing — unknown, the caller keeps its old trial-and-error path). Use `caps.lacksExtension("x")` (a *known* no) to skip an endpoint, never `!hasExtension` (that is also true while unknown). A plain Subsonic server counts as known-with-none. The first probe per server writes a `NOTE Env server: … ; extensions: …` line, and Copy Diagnostics lists the extensions. Readers: lyrics (`songLyrics`) and seek-by-reopen (`transcodeOffset`, via `canSeekByTimeOffset()`).
- **Random Mix is a context-menu action, not a category node** — a category node above the artist list never rendered under Wine (root cause never pinned down, emoji-in-title theory ruled out). If a future smart-list category node silently fails to render, don't assume the same cause.

- **An artist's "Top Songs"/"Similar Artists" child nodes must stay out of `collectSongsDeep`'s recursion into their parent Artist.** They're extra browsing entry points (`BrowserNode::CatArtistTopSongs`/`CatArtistSimilarArtists`, injected by `fetchChildren`'s `Artist` case), not part of the artist's discography — walking them as part of a "Play/Add whole artist" would pull in duplicate top tracks and drag in unrelated artists' entire catalogs (via Similar Artists → their own albums → songs). `collectSongsDeep` filters them out of a *parent*'s recursion (`isArtistSubCategory`); selecting either node directly still expands normally, since the filter only applies to iterating another node's children, not to the node itself.

- **A category/tree node's children only render after a real `fetchChildren` round-trip** — both platforms' expand handlers (`OnTreeExpanding` on Windows, `outlineViewItemWillExpand` on Mac) skip entirely once `childrenLoaded` is already true, and the actual tree-item insertion only happens from that fetch's completion callback. Pre-populating `node.children` ahead of time (e.g. to save a request) renders nothing — this is why Podcasts is a genuine two-level lazy tree (`CatPodcasts` → channel list → each channel's own expand fetches its episodes) instead of one `getPodcasts.view?includeEpisodes=true` call.

- **Podcast episode playability is gated by a bare id, not a separate flag** — `makePodcastEpisodeNode()` only sets the node's `id` to the episode's `streamId` once the server reports `status == "completed"`; otherwise `id` stays empty. `collectSongIdsDeep()` already drops id-less nodes (`NavidromeBrowserModel.cpp`), so an undownloaded episode is automatically un-enqueueable with no platform-side special-casing — `infoText` just shows the status so the user knows why.

- **`make win-build`/`win-build-local.sh` doesn't restart Wine foobar2000** — a replaced DLL under a still-running process is silently ignored until restart. Use `make win-build-launch`.

- **`win-build-local.sh`'s force-included `win_prefix.h` is load-bearing.** `WinSock2.h` must precede `windows.h` (pfc-lite.h's winsock include clashes with legacy `winsock.h`); `timeapi.h`/`winioctl.h` aren't pulled by `windows.h` but pfc/helpers need them; `_NO_SYS_GUID_OPERATOR_EQ_` must be defined *before* `windows.h`, because pfc-lite.h sets it too late to stop `<guiddef.h>`'s non-constexpr GUID `operator==` and the 2026-09-16 SDK's `static_assert(guid1==guid2)` in `guid.cpp` needs pfc's constexpr one. `pfc/audio_math.cpp` gets `-mavx2 -mfma` (clang refuses SIMD intrinsics without the target feature; pfc dispatches at runtime, so it's safe).
- **`win-build-local.sh`'s object cache tracks headers and flags** (it didn't until 2026-10: keyed on the `.cpp` mtime only, it twice shipped a stale-ABI DLL after a shared-header edit — see [[windows-build-cache-header-staleness]] memory). Each compile writes a clang depfile (`/clang:-MMD`, `build-win/obj/*.d`); `obj_is_fresh()` reuses an object only while its source and every listed header are older and still exist, and `obj/.flags` (sha1 of `CL_COMMON`) drops the whole cache when the flags change (`--release-log` and back). Anything regenerated every run that every TU includes must be written only on change — `win_prefix.h` (`cmp` before `mv`) and `version_generated.h` (`version.sh`) are — or every build becomes a full rebuild. `--clean` is left for toolchain swaps (xwin CRT/Windows SDK and WTL headers come in via `-imsvc`, so `-MMD` leaves them out of the depfile; the foobar2000 SDK/pfc headers are `-I` and tracked). A crash with an offset and no code-side explanation: still try `--clean` once. Symbolize with `llvm-symbolizer --obj=foo_navidrome.dll --relative-address -f -C <offset>` against a `/Z7 /debug:full` rebuild (debug-only flags, don't leave them in — ~25% size bloat).

- **Bulk Win32 tree rebuilds go through `TreeRebuild` + `clearTree()`** ([issue #30](https://github.com/santiagorod92/foo_navidrome/issues/30)). `DeleteAllItems()` with a selected item makes the TreeView move the caret to the next item on every deletion, one `TVN_SELCHANGED` each, and `OnTreeSelChanged` walks the whole tree (`clearSelectionExcept`), so a search froze foobar2000 for O(N²): 2.3 s with 1500 root rows on Win11. `clearTree()` deselects first (`SelectItem(nullptr)`) and resets `m_selAnchor`; `TreeRebuild` (RAII) sets `m_treeRebuilding`, which makes `OnTreeSelChanged` a no-op, and wraps the inserts in `SetRedraw(FALSE/TRUE)`. Measured: search 2287→9 ms, clear 397→30 ms, root load 495→27 ms. Any new code that clears or fills the tree in bulk uses both. `make win11-ui ARGS=search` (deploy, select a row, search, clear) fails when either rebuild takes over `SEARCH_MAX_MS` (500); the dev server has ~70 artists, so a scale check needs a temporary padded build. macOS's `NSOutlineView` reloads in one call and isn't affected.

- **Reading the tree control off the UI thread is a cross-thread call.** Every background action captures selection on the UI thread first, passes the node vector into the worker (`collectSongIdsDeep` takes pre-captured nodes). Same rule for macOS `-selectedNodes`/`-parentForItem:`.

- `cfg_int`/`cfg_bool` must be qualified `cfg_var_modern::cfg_int`/`cfg_bool` — unqualified resolves to the legacy variant (no `set()`, different serialization) on Windows SDK headers; Windows fails to build, macOS compiles fine. `cfg_string` has no such ambiguity.

- **Don't use libPPUI symbols (`WIN32_OP`, `libPPUI/*.h`) in the DLL** — `win-build-local.sh` compiles `../libPPUI` sources in, but `foo_navidrome.vcxproj` has no libPPUI `ProjectReference`, so CI's MSBuild fails at link (`unresolved external symbol WIN32_OP_FAIL`) while every local build is green. Throw `exception_win32(GetLastError())` (pfc) instead.

- **Include a cross-component service header (`NavidromeRatingService.h`, `NavidromeLibraryService.h`, `NavidromeLyricsService.h`) from exactly one `.cpp`, `NavidromeServices.cpp`.** Each defines its `class_guid` in the header. When `main.cpp` was split, every topic file kept the old include list: the Windows lld-link accepted the duplicates silently, and the Mac link failed with `duplicate symbol '__ZN9navidrome20navidrome_lyrics_api10class_guidE'`.
- **The "refresh ratings on startup" advconfig switch moved from GUID tail `0x01,0x0e` to `0x01,0x18` (2026-10-15).** It shared `0x01,0x0e` with the File › Bookmark command and the Mac browser `ui_element`; moving it was the change that loses the least user state (a user who had switched it off sees it on once). Check `NavidromeGuids.h` before taking a tail.

- **`std::min`/`std::max` need parens on Windows:** `(std::min)(a, b)` — `windows.h` macros `min`/`max` otherwise mangle the call. macOS compiles the bare form fine.

- **Adding a `src/platform/win/*.cpp` only needs a `src/platform/win/foo_navidrome.vcxproj` edit** — both clang-cl build scripts derive their source list from the vcxproj via `scripts/component-sources.sh`. A *moved/renamed* file still needs the vcxproj edit, and `component-sources.sh` resolves every `Include=` relative to the vcxproj's own folder (so `..\..\core\X.cpp` works). Tested helpers also need `tests/MediaEnrichmentTests.vcxproj` + `run-unit-tests.sh`.

- **Cover-art cache (`CoverCache`) and ESLyric config need explicit invalidation on credential/header changes** — keyed from server URL+user+token at last save, not read live. `NavidromePluginWin.cpp` clears/reinstalls both in `NavidromeHeadersWindow::OnSave` and `NavidromePrefsInstance::apply()`. Any new place credentials change needs the same two calls.

- **`install-macos.sh` must prefer Release over Debug** — DerivedData often has a stale Debug `.component`; `find_component()` filters `*/Products/Release/*` first, then sorts by mtime.

- macOS ships bash 3.2: `"${EMPTY_ARRAY[@]}"` under `set -u` is an unbound-variable error. Use explicit if/else or `"${ARR[@]+"${ARR[@]}"}"`.

- **Never run `mac-dev-build.sh`/`install-macos.sh` while foobar2000 is running** — replacing/re-signing the `.component` under a live process causes `EXC_BAD_ACCESS (SIGKILL (Code Signature Invalid))` on the next touched page, with a crash report pointing at unrelated code. Tell it apart from a real crash: termination namespace is CODESIGNING, fault is at offset `+0` of some function. Quit foobar2000 first.

- Bundle directory mtime doesn't update on `cp -Rf` — check the inner binary (`Contents/MacOS/foo_navidrome`) mtime when verifying an install.

- **No unified "Library viewers" list page on foobar2000 v2 Mac** — each `library_viewer` registers its own `preferences_page` parented to `guid_media_library` to get an entry point there. `library_viewer.get_preferences_page()` must return that Media-Library-parented GUID, not the Tools-parented one.

- **No debugger attach for foobar2000 components (Mac or Wine)** — logging is the primary diagnostic channel, and it ships: `NAVIDROME_LOG`/`WARN`/`ERR`/`NOTE`/`TIMER` (`NavidromeDebugLog.h`, header-only, `dbg::Logger`) are active in every build. **Release** (CI, what users install): `<profile>/foo_navidrome.log` (path set by `NavidromeLogInit::on_init` in `main.cpp`; lines before that are buffered and flushed), WARN+ only, INFO while *Advanced › Tools › Navidrome: verbose logging* is on (advconfig GUID tail `0x05,0x01`, read per line → no restart), rotated to `.1` past 2 MB. **Dev** (`NAVIDROME_DEBUG_LOG`, set by `win-build-local.sh`/`mac-dev-build.sh`): `/tmp/foo_navidrome_debug.log` from the first line, INFO, 8 MB — `make win-logs`/`make mac-logs` and the UI smoke tests read it. `make win-build-release-log` (`win-build-local.sh --release-log`; the flags stamp rebuilds everything on the switch) builds the release flavour under Wine. A `NOTE` line (always written) opens each session with component/foobar/OS/arch/Wine versions; a `==== YYYY-MM-DD ====` marker is written when the date changes. The last 300 lines also live in memory (`recentLines()`) for **Copy Diagnostics** (Preferences › Tools › Navidrome, both platforms: `collectDiagnostics()` in `main.cpp` → `buildDiagnostics()` in `NavidromeDiagnostics.h`, pings via `libraryCore().serverInfo()`; **Open Log Folder**/**Show Log in Finder** beside it). The diagnostics text is pasted into public issues: host replaced by `<server>`, `scrubAuth` re-applied, custom headers reported as set/none only. `.github/ISSUE_TEMPLATE/bug_report.yml` walks reporters through verbose logging → reproduce → Copy Diagnostics; keep its menu paths and button labels in sync with the prefs pages. Tags: `UI`, `HTTP`, `API`, `Input`, `Scrobble`, `Rating`, `Bookmark`, `Env`, `Playlist`, `Art`, `Lyrics`, `AudioMuse`, `PlayQueue`. Env knobs (read once, override the defaults): `NAVIDROME_LOG_LEVEL`, `NAVIDROME_LOG_TAGS`, `NAVIDROME_LOG_MAX_MB`. **Any new line printing a URL must call `navidrome::dbg::scrubAuth()` first** — redacts `t`/`s`/`p`/`u`/`apiKey` query values and URL userinfo; the file now sits in users' profiles. Because the macros are no longer compiled out, keep INFO lines off per-sample/per-chunk paths. No `<windows.h>` in the header (CRT `_wfopen_s`/`_dupenv_s` only) so the SDK-free test host includes it on every toolchain. `navidrome::dbg::runGuarded(tag, what, fn)` wraps detached-thread bodies in try/catch — an escaping exception there is `std::terminate`.

- **Unified HTTP error model:** `navidrome::ErrorKind`/`Error` in `SubsonicTypes.h`. `isRetryable()` covers `Network`/`Timeout`/`RateLimited`/`ServerError`; every retry loop on both platforms shares the same policy via `navidrome::retry` (`kMaxAttempts`=3, `again()`, jittered backoff `backoffMs()` = `300ms·n + jitter[0,200)`) — never reimplement a local max-attempts constant or backoff formula, share the namespace instead. `Auth` outcomes print a once-per-session console warning (`navidrome::warnAuthRejectedOnce()`, `main.cpp`, called from both transports' `onAuthRejected()`). The main JSON request path retries inside `SubsonicCore.cpp`'s loop (jitter from `IHttpTransport::jitterMs()`, a default `std::mt19937` impl neither platform overrides). Outside that path, the two platforms diverge by design: Windows' `httpGetBinary`/`httpDownloadToFile` (WinHTTP, `WinHttpHandle` RAII wrapper) get RAII+logging but no retry — cover art is cached/best-effort, downloads are user-initiated with visible errors; macOS's `-dataForURL:` (the separate bare-byte cover-art fetch) *does* retry, but through the same `navidrome::retry` primitives via the client's own `_transport` — no local reimplementation.

- **`navidrome://track/<id>` parse/build is one shared implementation** (`SubsonicTypes.h`). Building has exactly one caller (`enqueueBrowserNodes` in `NavidromeBrowserEnqueue.cpp`); input handlers only parse. Plain string scan, not `NSURLComponents` (which mis-parsed `track` as authority) — future scheme growth (e.g. `navidrome://playlist/<id>`) should branch on the segment right after `navidrome://`.
  - **Encoder is strict RFC-3986** (unreserved chars only) — a Mac-built URI for a track with `! * ' ( )` in title/artist changes byte-for-byte vs the old `NSURLQueryAllowedCharacterSet` encoding. Since the URI is the `playable_location`, that's a one-time cosmetic dedup miss on upgrade for affected rows, not data loss.

- **A song node's `displayName` is the title written to the playlist** — `enqueueBrowserNodes` puts it in the URI and the `title` hint. Build song nodes with `navidrome::makeSongNode()` and put any extra row text in the label (`BrowserWindow::labelFor`), never in `displayName`: Windows search once set `displayName = title + " — " + artist` and every searched track landed in the playlist titled "Thunderstruck — AC/DC".

- **`get_info()` is NOT the display path for a freshly enqueued track — the metadb hint list is.** Any field added to `get_info()` must also go in the hint block (`file_info_impl` pushed via `metadb_hint_list`) or it stays blank until a forced info reload. `NAVIDROME_RATING`/`NAVIDROME_STARRED` are set in both places for this reason.

- **Don't name an exported field `rating`** — collides with foobar's own Playback Statistics `%rating%` provider (SDK warns overlaying a standard field has "severe ill effects", undefined precedence). Server values export under `NAVIDROME_` prefix. Same reasoning for any future exported field.

- **A URI-embedded value can only be refreshed through metadb, never by rewriting the URI** — a changed query param is a new `playable_location`, i.e. a duplicate playlist entry, not an update. `syncRatingsToPlaylists()` uses `metadb_hint_list_v3::add_hint_forced()` (forced because a normal hint is skipped when the file hasn't changed by timestamp, which a URI never does). Consequence: metadb and the URI now disagree, so a user-forced full info reload regresses to the enqueue-time snapshot — never to garbage.

- **The rating refresh must not sit behind `cfg_scrobble`** — it's a display concern, not a play report. `navidrome::ScrobbleTracker::onNewTrack()` returns `{refreshRatingId, scrobbleNowId}` separately; `refreshRatingId` fires for every one of our tracks regardless of the scrobble pref.

- **Startup refresh groups by album** — `getAlbum.view` returns `userRating` for every song in one request, collapsing the pass to one request per distinct album (`getSong.view` has no multi-id form). That's the only reason `albumId=` is in the URI; the input handler never reads it back. Entries written before this existed can't be grouped and are skipped (counted, reported, never swallowed) — they still catch up via rate/star, browse, playback, or a sibling entry from the same album.

- **`init_stage_callback`/`FB2K_ON_INIT_STAGE` never dispatches on macOS** — silent no-op, no error, no console output. Use `initquit::on_init` instead (fires both platforms; playlists are already loaded by then).

- **Report skipped coverage, stay quiet about user-chosen states.** Startup refresh has four no-op paths: switch off / no server configured (user's choice, don't log every start) vs. no album id / skipped-after-partial-run (leaves entries behind, must log counts).

- **Every context-menu action's failure branch must `NAVIDROME_WARN("UI", …)`, not just `setStatus`/error label.** Star/unstar, rate, playlist CRUD (add/create/remove/rename/delete, send active playlist), bookmark removal, radio station CRUD (browser menu *and* the Radio Stations prefs page) and podcast subscribe/unsubscribe on both platforms log the error string when the underlying call fails — `setStatus`/`_statusLabel` alone is invisible once the window closes, and it's the only record when a user reports "X didn't work" after the fact. Log from the worker, before the hop to the UI thread (op name + target + error). Any new mutating action needs the same one-liner.

- Startup refresh's off switch is an `advconfig_checkbox_factory` (*Preferences › Advanced › Tools*), not a `cfg_bool` — avoids UI work on both prefs dialogs and the `cfg_var_modern::cfg_bool` qualification trap.

- **Any code consuming `navidrome://` URIs must be updated when the scheme changes** — the art extractor's `is_our_path` once only matched legacy `/rest/stream.view` URLs and silently broke (missing cover art, no error) when the scheme moved to `navidrome://`. Audit `strstr`/`strncmp` calls in `*.mm`/`*.cpp` whenever the URI scheme is touched.

- **`NSViewController` multi-mount pattern:** foobar's Mac prefs pages and `ui_element_mac::instantiate()` both just take a `fb2k::wrapNSObject`-wrapped `NSViewController`. Never share one VC instance across mount points (Cocoa: one superview per view) — each mount creates its own; data sharing is at the model layer. `ui_element_mac` may call `instantiate()` more than once per session (dock/undock/split) — never cache a VC across calls.

- **No release loop to prevent any more:** the release pushes only a tag, never a commit to `main`; `concurrency: { group: release-${{ github.ref }} }` still serialises runs so two can't race on the same tag.

- **`mac-dev-build.sh` vs `mac-ci-build.sh` — don't merge them.** Dev script bumps version + installs to `~/Library/foobar2000-v2/`; CI script takes version as an arg, builds into hermetic `build/derived/`, never touches `~/Library`.

- **PCH needs `#include <string>`/`<string_view>` in `stdafx.h` before `<helpers/foobar2000+atl.h>`** — `pfc/string-interface.h` relies on transitive includes that Xcode 15.4/macOS14 SDK (GH Actions `macos-14` runner) doesn't provide, unlike newer toolchains. Don't try to fix this in pfc upstream (not our fork).

- **Never pipe `xcodebuild` output through `tail` in CI** — scrolls the actual `error:` lines off. `mac-ci-build.sh` redirects full log to `/tmp/xcodebuild.log`, prints a filtered summary, and on failure re-prints `grep -B3 error:` at the very end (GH Actions reads failed-job output bottom-up). `release.yml` also uploads the full log as an artifact on failure.

- **`foo_navidrome.xcodeproj`'s link against `pfc` is a hand-typed filename, not a real cross-project target reference — it breaks silently whenever upstream renames the target.** `foo_navidrome`'s `PBXFileReference` for pfc is a plain `path = "libpfc.a"; sourceTree = BUILT_PRODUCTS_DIR;` entry (no `PBXReferenceProxy`/`PBXContainerItemProxy` into `pfc.xcodeproj`), and the target itself has an empty `dependencies = ()` — there is no formal Xcode dependency on pfc at all. It has only ever worked because Xcode's implicit-dependency resolution matches library names against product filenames of every target in the workspace. On 2026-09-22 this broke two ways at once, diagnosed from a real CI log (`gh run view --log-failed`), not guesswork:
  1. **No shared scheme was ever checked in** (`foo_navidrome.xcodeproj/xcshareddata/xcschemes/` didn't exist), so every headless `xcodebuild -workspace … -scheme foo_navidrome` in CI auto-generated a throwaway scheme — and at some point (likely a GH Actions `macos-14`/Xcode toolchain image update) that stopped reliably including `pfc` in the implicit-dependency build graph: zero `Libtool`/compile lines for it anywhere in the failing log. **Fix:** a committed shared `.xcscheme` with explicit `BuildActionEntries` for all 6 workspace targets (`foo_navidrome`, `pfc`, `foobar2000_SDK`, `foobar2000_SDK_helpers`, `shared`, `foobar2000_component_client`) plus `buildImplicitDependencies="YES"` — stop depending on autocreation. Once fix (1) made Xcode actually *try* to build `pfc`, the link still failed (`ld: library 'pfc-Mac' not found`) because the filename our `PBXFileReference` hardcodes no longer matches what upstream produces. **Fix:** update the hardcoded `libpfc-Mac.a` → `libpfc.a` in `foo_navidrome.xcodeproj/project.pbxproj` (4 occurrences: `PBXBuildFile`, `PBXFileReference`, and their two membership-list entries) and the scheme's matching `BuildableName`/`BlueprintName`.
  - **If this breaks again after another upstream SDK sync**, don't assume it's the scheme — first fetch the live `pfc.xcodeproj` from `reupen/foobar2000-sdk-unmodified` and diff its `pfc` target's `name`/`productName` against what `foo_navidrome.xcodeproj`'s `PBXFileReference` hardcodes; a rename there is a silent, external, un-diffable (from our side) breaking change with no corresponding commit in *this* repo to point at.

- **Minimum macOS is 12.0, and the deployment target has to be forced on the xcodebuild command line.** Xcode 26+ refuses any target below 12.0 outright (`error: The macOS deployment target 'MACOSX_DEPLOYMENT_TARGET' is set to 11.0, but the range of supported deployment target versions is 12.0 to 27.0.x`), and it is not only our project that declares 11.0 — every SDK project in the workspace (`foobar2000_SDK`, `foobar2000_SDK_helpers`, `shared`, `foobar2000_component_client`, `pfc`) does too. - **This same upstream SDK sync also bumped `pfc-lite.h`'s minimum language standard from C++17 to C++20** (`#if _MSVC_LANG < 202002L` / `#if __cplusplus < 202002L`, was `201703L`) — intentional, per the official changelog (foobar2000.org/changelog-sdk, 2026-09-16): *"C++20 is now widely used, a C++20 compatible compiler is required."* Every toolchain that compiles against real `pfc`/SDK headers needs `/std:c++20` or it's `error C1189: #error: C++20 please` before a single one of our own files even compiles. Four places hardcode the standard and all four had to move together: `src/platform/win/foo_navidrome.vcxproj` and `tests/MediaEnrichmentTests.vcxproj`'s `<LanguageStandard>` (now `stdcpp20`), plus `scripts/win-build-local.sh` and `scripts/win-build-mac.sh`'s clang-cl `/std:c++20` flag. `scripts/run-unit-tests.sh`'s two `-std=c++17`/`/std:c++17` flags (mac-test and Linux `make test`) were deliberately left alone — that path is genuinely SDK/pfc-free (no foobar2000 siblings needed), confirmed still green at C++17 through this exact incident, so there's nothing to bump there; don't cargo-cult the change onto it.

- **Same SDK sync a third time: `pfc.lib`'s ARM64EC build now needs `pfc_crashHook`/`pfc_winFormatSystemErrorMessageHook` (extern "C") wired in, and nothing does it for us.** Confirmed intentional against the official changelog (foobar2000.org/changelog-sdk, 2026-09-16): *"PFC: Refactored redirection of PFC methods to shared.dll, 'FB2K Debug' / 'FB2K Release' build configurations are no longer required."* (same entry as the C++20 bump above). `foobar2000/shared/wrap_pfc_hooks.h` implements the redirect (its own comment: *"Inclusion of this header enables the redirect"*) — it's a new required integration step, not a bug, but `reupen/foobar2000-sdk-unmodified` ships the SDK exactly as its name says: raw, with no `#include` of it wired into any of the `shared` project's own `.cpp` files, so `shared.vcxproj`'s ARM64EC link fails with unresolved externals until something adds it (x64/Win32 don't reference the EC-only symbols, so they're unaffected). We can't edit the SDK's own vcxproj sources (checked out fresh every run, not vendored here), so `build-windows.yml` does the wiring post-checkout: appends `#include "wrap_pfc_hooks.h"` to the freshly-staged `foobar2000/shared/stdafx.cpp` (a single-TU file, matching the header's own single-definition contract) in its own step, right after "Move SDK subdirs into the expected sibling layout". **Use `printf '\n#include …\n' >>`, not `echo … >>`** — `stdafx.cpp` ships with no trailing newline, so a bare `echo >>` glues straight onto the existing `#include "shared.h"` line into one corrupted directive that silently never includes the new header (caught in a real CI log: the step's own diagnostic `cat` printed one mangled line, build still failed with the exact same unresolved externals). `release.yml` (macOS) doesn't need the same patch — the header is `#ifdef _WIN32`-guarded. If a *future* SDK sync ever moves this redirect somewhere our patch doesn't reach (or reupen starts wiring it themselves), re-check `foobar2000.org/changelog-sdk` first — it documents intentional SDK changes like this in plain English, faster than reverse-engineering a link error from a diff of two third-party repo snapshots.

- **The C++20 bump also broke every `u8"…"` literal in the unit tests (then one `tests/MediaEnrichmentLogicTests.cpp`, now split per module)** — C++20 makes `u8"…"` a `const char8_t[]`, not `const char[]` like C++17 (a deliberate, well-known C++20 breaking change, correctly enforced by MSVC once `/std:c++20` took effect), so every `u8"café"`/`u8"中文…"` test literal stopped implicitly converting to the `std::string`/`const char*` parameters our own helpers take (`error C2664`/`C2088`/`C2446`/`C2440`, ~10 call sites). Fix: drop the `u8` prefix — plain `"café"` is still UTF-8 bytes as `const char[]` (the file is saved UTF-8, `/utf-8` is set project-wide), functionally identical to the old `u8"café"` pre-C++20 and exactly what the `std::string`-based API surface expects. If a future edit reaches for `u8"…"` here for "correctness," it'll silently reintroduce this — there's no legitimate use for actual `char8_t` anywhere in this codebase, everything is `std::string`/`char`.

- **SDK source in CI is `reupen/foobar2000-sdk-unmodified`, not `marc2k3/foobar2000-sdk`** — the latter (redirects to `javascript-panel/foobar2000-sdk`) is missing `helpers-mac/`, needed for `NSView+embed.m`. Staging layout: `_sdk-staging/foobar2000/<dir>` → `foobar2000/<dir>` (one level deeper), `_sdk-staging/pfc` → `pfc` (at staging root).

- **Windows-on-ARM (Mac container) x64 traps:** (1) `clang-cl` misparses a leading `/Users/...` path as `/U` flag → pass sources as `/Tp<path>`; (2) local x64 build must use static CRT (`/MT`) — ARM foobar only bundles ARM64EC runtime DLLs, an emulated x64 `/MD` DLL fails to load silently; (3) the ARM build loads x64 components from `<profile>/user-components-arm64ec/<name>/`, so a loose DLL copied there loads (verified 2026-10-17, `win11-arm.sh deploy`); a `.fb2k-component` passed on the first launch is instead taken for a file to play; (4) QEMU guest needs `-device intel-hda` or playback dies before decode.

- **UI tests assume an English UI, and restore what they change.** The window title and `-command:` names they use are translated, so `restart()` switches a profile set to another language to `UI_LANG` (default `en`) for the run; "automatic" is left alone (the system must be English). Changes a scenario makes to the profile are undone through `on_exit` (a stack run by one `EXIT` trap — playqueue's stream format, cui's UI module, i18n's language, solo's moved component and UI module). `i18n` sets `UI_LANG=es` and drives the Spanish command and title. The confirmation popups log `UI ... confirmation: toast|dialog (<title>)` from the shared `showConfirmation()` (was tagged `PlayQueue`).
- **`solo` moves the sister component out of the profile, not just aside.** foobar2000 loads every subfolder of `user-components*`, so a renamed folder there would still load: it goes to `<profile>/.solo-off-<name>`, and a run that died halfway is detected (the `.solo-off` copy without the original) and treated as already moved. It also deletes the active UI module rows for the run, so foobar2000 starts the Default UI instead of looking for Panels UI. foo_ui_panels has the mirror scenario (`ui-test.sh <platform> solo`, `navidrome=no` in its session banner).
- **UI tests (`scripts/ui-test.sh <platform> <scenario>`) — how they drive the UI.** A scenario only calls the `d <action>` driver; adding a platform action means one `<platform>_<action>` function per platform (or a `return 2` "can't on this platform" the scenario treats as a warning, like `mac_window_exists`). `ok`/`fail`/`note` also append to `$RESULTS` (TSV) for `compare`. The user's play queue on the server is shared by every platform, so `playqueue` holds a host `flock` (`$TMPDIR/foo_navidrome-playqueue.lock`) from Save to Restore: parallel runs (`PARALLEL=1`, or several agents) stay correct. Wine: `tools/wclick.c` (from foo_ui_panels, built on demand into `build/tools/`) runs inside the Wine prefix and *posts* messages to `foo_navidrome_BrowserWnd`'s deepest child at a client point, so the host's mouse is never touched. Posted keys do nothing until a click has given the tree a selection, so the scenario clicks the first row (`FIRST_ROW_Y`) first. The browser is opened with `foobar2000 "-command:Open Navidrome Browser"`, and Enter closes it afterwards (the screenshot then falls back to the main window). macOS: real VNC input via `mvm`. The File menu is clicked at fixed screen coords, then type-select "Open N" + Enter. The list is keyboard-driven: Tab from the search field, Down × (12 category rows + 1) to the first artist, Right to expand. **Adding or removing a root category node shifts that count** (`CATEGORY_ROWS`). Under an artist, the first two children are Top Songs and Similar Artists, hence Down×3 to the first album. Log assertions only read lines written after the last `mark`. `ui-test.sh <wine|win11> prefs <page>` restarts foobar2000 into Preferences on one of our pages: it sets `preferences.lastOpenPage` with foobar stopped and cold-starts `foobar2000 -config`, the only way that opens Preferences under Wine. The Mac log checks need `mac-vm-build.sh --debug-log` (`MAC_EXTRA_CFLAGS` → `OTHER_CFLAGS`, unset in CI); without it the Mac scenario still runs but skips them. **`playqueue` scenario** (`make win-ui ARGS=playqueue`, `make mac-vm-ui ARGS=playqueue`): plays an album like `smoke`, then runs File › Save / Restore Play Queue and asserts the resume seek. Our own main-menu commands are reachable with `foobar2000 "-command:<name>"` on a running Wine instance (the Mac side types the name into the File menu); the Wine run sets the stream format to `PLAYQUEUE_FORMAT` (default `opus`) with foobar stopped and puts the old value back on exit. `foobar2000 "/context_command:Properties" <uri>` does **not** reach a running Wine instance, so a track's Properties dialog can't be scripted there.
- **Local AudioMuse-AI test stack (`dev/audiomuse/`, `make audiomuse-*`, `scripts/audiomuse-dev.sh`) uses host networking for flask + worker on purpose.** The dev box's Ollama (Instant Playlist's LLM) is a systemd service on `127.0.0.1:11434` only, and ufw (default deny incoming) drops bridge-network → host traffic, so a bridged container can't reach it without root changes (a socat relay on the docker0 IP was tried: it listens fine but ufw eats the packets). With `network_mode: host`, AudioMuse reaches Ollama at `127.0.0.1:11434` and Postgres at its loopback-published `127.0.0.1:5433`. The API is always `:8000` (gunicorn bind is hardcoded in the image). The Mac VM guest would need a ufw allow rule for `:8000`. Everything is configured from env (`MEDIASERVER_TYPE`/`NAVIDROME_*`, `AUDIOMUSE_USER/PASSWORD` + `API_TOKEN` + `JWT_SECRET` with `AUTH_ENABLED=true`), which skips AudioMuse's setup wizard. `.env` is gitignored and holds real Navidrome credentials.
- **AudioMuse persists its config in Postgres (`app_config`) on first start, and the stored values win over the env afterwards** — changing `.env` later silently does nothing (an old `OLLAMA_SERVER_URL` kept pointing at a removed container). `audiomuse-dev.sh up` re-syncs the LLM keys (`sync_llm_config`) and restarts flask/worker when they differ; any other env setting that must change after first start needs the same treatment or `make audiomuse-down ARGS=-v` (wipes the analysis too). A failed LLM call still answers HTTP 200 with a non-AI fallback playlist — check the flask log (`provider=... url=...`, `Error calling Ollama`) before trusting a fast Instant Playlist.
- **WinHTTP: a long POST needs its timeouts on the request handle, including `WINHTTP_OPTION_RECEIVE_RESPONSE_TIMEOUT`.** `WinHttpSetTimeouts` on the session didn't cover the wait for response headers; under Wine an AudioMuse Instant Playlist died at ~21 s with `winhttp err=10060`. `WinJsonPoster` sets both on the request (verified with a 30 s LLM answer). The Navidrome GET path is unaffected (short requests).
- **Columns UI is tested on the Win11 VM, not Wine** (`make win11-ui ARGS=cui`: deploy, relaunch, assert the browser panel's `Columns UI panel instantiated` line + artist load, the lyrics panel's `Columns UI lyrics panel instantiated`, then Play and a `panel shows N line(s)` line, crash/ERROR checks). The guest's Columns UI layout has both panels: the lyrics one was added once with *Live layout editing* › right-click the playlist › *Add after* › *Panels* › **Navidrome Lyrics** (a CUI layout lives in its own config, so switching UI modules keeps it). Under Wine, foobar2000's restart after the *New user interface module(s) found* dialog never completes (the old process spins on one thread), and in a profile copy whose exe is a symlink (the AUR `~/.foobar2000` is) the restart relaunches the symlink target's install, i.e. the real profile. One-time VM setup: `wvm deploy --gh reupen/columns_ui@v3.7.0`, pick Columns UI in that dialog, then *Live layout editing* › right-click › *Add after* › *Panels* › **Navidrome Browser**. foobar2000 stores the active UI module GUID in `cfg_var.22AF8F41-…`/`cfg_var.094A28DA-…` (blobs, raw little-endian GUID). Setting them alone doesn't skip the *new UI module found* dialog, but switching between modules already known works: `cui` writes Columns UI's `{F12D0A24-A8A4-4618-9659-6F66DE067524}` there for the run and restores the previous one (the guest's daily UI is Panels UI, which silently broke the old `cui` scenario).
- **A short confirmation needs a different call per platform** (Save Play Queue, found by running `playqueue` on all three and looking at the screenshots). Windows: `popup_message` opens a resizable read-only text viewer with no OK that Enter doesn't close, and so does `fb2k::popup_toast` (it exists on Windows 2.26 but falls back to that same viewer), so Windows uses `popup_message_v3::query_t` with `buttonOK`: a small dialog, Enter closes it. macOS: that dialog shows without key focus and its OK isn't the default button, so Enter does nothing; macOS uses `fb2k::popup_toast` (a real toast, `#ifdef __APPLE__`). Errors keep `popup_message` everywhere (long text, copyable). Lesson: the log line said "toast" on both platforms while they behaved differently; check the screenshots, not just the log.
- **Driving a foobar2000 context/popup menu with `wclick` (Wine):** `menukey:VK` still needs a `top:` window that exists (it falls back to the Navidrome Browser, which is usually closed by then) — pass `top:<main window title>`, e.g. `wclick 0 0 "top:Artist - Title" menukey:0x4E`. Right-click a playlist row with `top:<main window title>` + `r` (the title is the now-playing "Artist - Title"). foobar's `/runcmd-playing=`/`/playing_command:` don't reach a running instance under Wine — use the menu. A test cfg value can be written straight into `~/.foobar2000/profile/config.sqlite` (`configStrings`, key `cfg_var.<GUID>`) while foobar is **closed** (`foobar2000 -exit`); `preferences.lastOpenPage` = a page GUID makes Preferences open on it.
- **`pkill -f`/`pgrep -f` with a pattern that also appears in your own command line kills the calling shell** (exit 144). Use a bracket trick that the literal text can't match (`'foobar2000[.]exe'`), never `'[f]oo'` when the plain name also appears elsewhere in the same command.
- **macOS VM (`../macos-devbox`) traps:** x86_64 slice required (emulated Intel guest — universal CI build works, local arm64-only `mac-dev-build.sh` output doesn't; `mvm deploy` refuses it); macOS install is manual once (no unattended installer) — snapshot right after (`mvm snapshot base`, `mvm export base` for off-machine); the bundle is ad-hoc re-signed on deploy or macOS SIGKILLs it; diagnose a stuck boot from the screen (`mvm web` / `mvm shot`), not the container log; `mvm type` sends `:` as `;` and `mvm key cmd-comma`/`cmd-a`/`shift-semicolon` hang or do nothing on this guest keymap — set a URL-like value through the guest's `~/Library/foobar2000-v2/config.sqlite` (foobar quit first) instead of typing it.
