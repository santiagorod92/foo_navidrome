# foo_navidrome

## Overview

foobar2000 v2 component that browses and streams from Navidrome / Subsonic-compatible servers. Cross-platform: macOS (shipped) and Windows x86/x64/ARM64EC (shipped, runtime-verified on native Windows). One `.fb2k-component` carries all platforms. Two entry points on macOS: **File › Open Navidrome Browser** and **Preferences › Media Library › Library viewers › Navidrome**.

## Architecture

Shared C++ core + per-platform UI/HTTP layers:

- `main.cpp`, `stdafx.h`, `SubsonicTypes.h` — cross-platform shared code (component version, pure-C++ data types, `trackIdFromURI()` used by both scrobblers, `StarKind` / `AlbumListType` enums)
- `SubsonicClient.h/.mm` — macOS Subsonic HTTP client (ObjC/NSURLSession)
- `Windows/SubsonicClientWin.h/.cpp` — Windows Subsonic client (WinHTTP)
- `NavidromePlugin.mm` — macOS registration: `cfg_string` for URL/user/pass/salt, `preferences_page` under Tools, `mainmenu_commands` under File menu, `library_viewer` factory, and the **scrobbler** (`play_callback_static`)
- `NavidromeInput.h/.mm` — `input_singletrack` handler for the `navidrome://track/<id>?...` URI scheme. Parses metadata from the URI for `get_info()`; on `decode_initialize()`, resolves the current HTTP stream URL via SubsonicClient and opens a nested `input_decoder` via `input_entry::g_open_for_decoding(..., fromRedirect=true)`. Registered with `input_entry::flag_redirect`.
- `NavidromePlaylistSync.h` + its implementation in `main.cpp` — cross-platform, SDK-only. `syncRatingsToPlaylists()` walks every playlist, matches entries by `trackIdFromURI()`, and pushes fresh `NAVIDROME_RATING` / `NAVIDROME_STARRED` values onto them with a **forced hint**. `scanPlaylistAlbums()` collects the distinct `albumId=` values for the startup refresh and counts what it couldn't group. Lives in `main.cpp` because that file is already registered in all four build paths, so a shared SDK helper costs no build-system changes.
- `NavidromeArtExtractor.mm` — implements `album_art_fallback` so Now Playing / playlists show art fetched from Navidrome
- `Mac/NavidromeBrowserController.*` — `NSViewController` housing the Artists/Albums/Songs tree, search, action buttons. Mounted in three places: (a) directly inside the *Preferences › Media Library › Navidrome* prefs sub-page; (b) wrapped in a standalone `NSWindow` by `NavidromeShowStandaloneBrowser()` (called by the File menu and `library_viewer.activate()`); (c) as a dockable main-window layout panel via `ui_element_mac_navidrome` in `NavidromePlugin.mm`. Each mount point creates a fresh controller — Cocoa requires each `NSView` to have a single superview, so the previous shared-singleton pattern would have broken multi-mount. Enqueues tracks as `navidrome://` URIs (not raw HTTP URLs).
- `Mac/NavidromePreferencesController.*` — `NSViewController` preferences UI
- `Windows/NavidromePluginWin.cpp`, `Windows/BrowserWindow.*` — Windows ATL equivalents. Ported to the `navidrome://` URI scheme (`BrowserWindow::enqueueNodes` builds `navidrome://track/` URIs; `NavidromeInputWin` decodes them). `BrowserWindow` can mount two ways like the Mac controller: a standalone window (`show()`, singleton — File menu / `library_viewer`) **and** an inline `WS_CHILD` panel (`createEmbedded()`) hosted in the *Preferences › Media Library › Navidrome* sub-page. Right-click on the tree opens a Play Now / Add to Playlist context menu (`WM_CONTEXTMENU`).
- `Windows/MediaEnrichmentLogic.h/.cpp` — foobar-SDK-free helper module (URI/URL encode-decode, cover-art URL building, HTTP response classification, an LRU `CoverCache`, ESLyric `config.js` generation). Used by the Windows component only; the *tests* for it (`tests/MediaEnrichmentLogicTests.cpp`) build on Windows, Linux and macOS — the module's one platform-specific line is MD5 (`#if defined(_WIN32)` WinCrypt / `#else` CommonCrypto). Kept free of SDK types specifically so that test can build as a standalone host executable (see Development below). `NavidromeArtExtractor` (in `NavidromePluginWin.cpp`) is a real `album_art_extractor` (not a fallback) built on top of it, with results cached by (server, user, coverId).
- `Windows/EsLyricBridge.h/.cpp`, `Windows/EsLyricScript.h` — bridges to the third-party [ESLyric](https://github.com/esdatura/eslyric-fb2k) foobar2000 component, if installed (`%APPDATA%\foobar2000\profile\eslyric-data\` present). On startup and whenever credentials/headers are saved, writes a generated `scripts/lib/foo_navidrome/config.js` (server URL + Subsonic token, never the raw password) and a searcher script `scripts/searcher/navidrome.js` (embedded as `kEsLyricScriptSource`) that calls Navidrome's `getLyricsBySongId.view`, falling back to the legacy `getLyrics.view` artist/title lookup per-server once the by-id endpoint 404s. A no-op (empty error string) when ESLyric isn't installed.

GUIDs for cfg vars / prefs page / menu commands are hardcoded constants in `NavidromePlugin.mm` (lines 17–30) — must be regenerated when forking.

### Subsonic feature surface (both platforms)

Beyond browse/search/stream, both clients implement — with the same method names modulo language conventions:

| Feature | Endpoint(s) | Surfaced as |
|---|---|---|
| Scrobbling | `scrobble.view` | `play_callback_static` in `NavidromePlugin.mm` / `NavidromePluginWin.cpp`; `submission=false` on new track, `true` at `min(240s, length/2)`; gated on `cfg_scrobble` |
| Smart lists | `getAlbumList2.view` (newest/frequent/recent/random), `getStarred2.view` | Category nodes above the artist list in both browsers |
| Server playlists | `getPlaylists.view`, `getPlaylist.view` | "Playlists" category node → playlist nodes → songs |
| Playlist upload | `createPlaylist.view` + `updatePlaylist.view` | "Send Active Playlist to Navidrome" context-menu item |
| Playlist CRUD | `updatePlaylist.view` (`songIdToAdd` / `songIndexToRemove` / `name`), `deletePlaylist.view` | "Add to Navidrome Playlist ▸" submenu (+ "New Playlist…"), "Remove from Playlist", "Rename Playlist…", "Delete Playlist…" |
| Genres | `getGenres.view`, `getSongsByGenre.view` | "Genres" category node → genre nodes → songs |
| Favorites | `star.view` / `unstar.view` | Star / Unstar context-menu items; `★ ` prefix on the row |
| Ratings | `setRating.view`, `getSong.view`, `getAlbum.view` | Rating submenu (None, 1-5); trailing stars in the tree; exported to playlists as `NAVIDROME_RATING` / `NAVIDROME_STARRED`, refreshed on rate/star, on browse, on playback start, and at startup (album-grouped) |
| Transcoding | `stream.view` `format` / `maxBitRate` | Two prefs combo boxes (`cfg_stream_format`, `cfg_max_bitrate`) |
| Download originals | `download.view` | "Download Original Files…" context-menu item; folder picker, never transcoded |
| Bookmarks (resume playback) | `getBookmarks.view`, `createBookmark.view` (upsert), `deleteBookmark.view` | File-menu "Bookmark Current Position" (reads now-playing via `playback_control` + `trackIdFromURI()`); "Bookmarks" category node → songs with a trailing `⏱ m:ss` position; "Remove Bookmark" context-menu item |
| Internet radio | `getInternetRadioStations.view`, `createInternetRadioStation.view`, `updateInternetRadioStation.view`, `deleteInternetRadioStation.view` | "Radio" category node → station nodes; "New/Edit/Delete Radio Station…" context-menu items; **and** a dedicated *Preferences › Media Library › Navidrome › Radio Stations* sub-page (table + New/Edit/Delete) — `NavidromeRadioPrefsController`/`preferences_page_navidrome_radio` (Mac), `NavidromeRadioPrefsInstance`/`NavidromeRadioPrefsFactory` (Windows, in `BrowserWindow.cpp`) — independent of the browser tree, own fetch/own cache |
| Library scan | `startScan.view`, `getScanStatus.view` | "Rescan Library Now" button on the main *Preferences › Tools › Navidrome* page; kicks off a scan then polls `getScanStatus.view` every 1.5s until `scanning` goes false, showing "N processed" (Subsonic reports no total, so no percentage). `navidrome::ScanStatus` in `SubsonicTypes.h` (Windows client); Mac uses `-startScanWithScanning:count:error:` / `-getScanStatusWithScanning:count:error:` out-param methods instead of a shared struct, same convention as the rest of `SubsonicClient.h` |
| Play Similar | `getSimilarSongs2.view` (`id` = artist/album/song id, `count`) | "Play Similar" context-menu item on any artist/album/song row; fetches last.fm-derived recommendations and appends + plays them via the existing enqueue path (same semantics as "Play Now") |
| Random Mix | `getRandomSongs.view` (`size`) | "Random Mix" context-menu item (plain text, both platforms — see gotcha below), alongside "Send Active Playlist to Navidrome"; fetches 100 random tracks and appends + plays them, no selection required, same enqueue path as "Play Similar" |

Every playlist mutation that takes a list chunks ids **50 per request** (`navidrome::kPlaylistChunkSize` in `SubsonicTypes.h`). Subsonic passes ids on the query string, and the Windows client's `WinHttpCrackUrl` path buffer is 4096 wchars — a 200-track playlist in one URL silently truncates.

`getGenres.view` reports the genre name in the JSON field **`value`**, not `name`, and `getSongsByGenre` keys off that name (there is no genre id) — so `NavidromeNode.id` for a genre row holds the genre string itself.

Credentials persist via `cfg_string` (foobar2000 config store). Password is sent via Subsonic token auth (md5 of password + salt) by `SubsonicClient`.

## Development

`Makefile` at repo root wraps the scripts below as `make` targets (`make help` lists them). Targets follow an `<os>-<action>` scheme — the `win-`/`mac-` prefix is the only thing that varies, the action after it means the same on both and is wired to whichever script runs those steps for that OS. E.g. `make test` for the fast Linux clang-cl+wine unit-test loop (`make mac-test` runs the same suite natively on macOS), `make win-build`/`win-install` for the local Windows cross-compile, `make win-build-launch` to also relaunch the local Wine foobar2000 afterward (see gotcha below), `make mac-build`/`mac-release` for the macOS loop, `make win-vm-*` for the Windows-on-macOS VM flow. It's a convenience wrapper only — the scripts remain the source of truth for actual build logic; keep the Makefile's flags/paths in sync if a script's CLI changes.

### Build layout (siblings required, see README)

```
foobar2000/
  SDK/, helpers/, shared/, foobar2000_component_client/
  foo_navidrome/        ← this repo
pfc/                    ← sibling of foobar2000/
```

### macOS

1. Open `foo_navidrome.xcworkspace` in Xcode (must use the workspace, not the bare xcodeproj — pulls in SDK projects)
2. Build the `foo_navidrome` scheme
3. `./scripts/install-macos.sh` copies the built component into foobar2000's user-components dir
4. Restart foobar2000

### Windows

Visual Studio 2022. `Windows/foo_navidrome.vcxproj` — must update `<ProjectReference>` GUIDs to match the local SDK projects. Build Release|x64, copy `.dll` to `%APPDATA%\foobar2000\user-components\foo_navidrome\`.

### Unit tests (`tests/`, cross-platform — one source file, three toolchains)

`tests/MediaEnrichmentLogicTests.cpp` is a standalone console exe (no SDK, no `.sln`) covering `SubsonicTypes.h` (shared, byte-identical everywhere) and `Windows/MediaEnrichmentLogic.cpp`. `MediaEnrichmentLogic.{h,cpp}` still lives under `Windows/` because only that component links it — but it is SDK-free and its *only* platform-specific line is the MD5 primitive: `#if defined(_WIN32)` → WinCrypt, `#else` → CommonCrypto `CC_MD5` (the same one `SubsonicClient.mm` uses; the `#else` branch pragma-silences the `CC_MD5` deprecation warning so `-Werror` builds clean). Do **not** move `MediaEnrichmentLogic.*` — that hits the three-place SRCS-list trap (`foo_navidrome.vcxproj`, `win-build-local.sh`, `win-vm/build-mac.sh`); moving the *test* was safe (only the Makefile + `build-windows.yml` + the vcxproj's `..\Windows\` relative path point at it).

`scripts/run-unit-tests.sh [mac|win|auto]` is the single source of truth for the compile+run command (per-host toolchain). Callers:
- **Windows / MSVC:** `tests/MediaEnrichmentTests.vcxproj`, Release|x64 — the one path that does *not* go through the script (needs real MSBuild). `build-windows.yml` runs it every CI run.
- **macOS:** `make mac-test` → `run-unit-tests.sh mac` — plain `clang++ -std=c++17 -Wall -Wextra -Werror`. Also run by `mac-dev-build.sh` before every `xcodebuild`, and by `release.yml` on the `macos-14` runner before its build.
- **Linux:** `make test` → `run-unit-tests.sh win` — `clang-cl` + `xwin` SDK + wine, no foobar SDK/pfc/libPPUI siblings needed (`$XWIN_SDK` defaults to `~/.local/share/xwin/sdk`). Also run by `win-build-local.sh` before the component compile.

So **both local build scripts gate on the tests** (`--no-test` to skip); a broken shared helper fails before the long component build. Add every new assertion once, to `tests/MediaEnrichmentLogicTests.cpp` — all hosts pick it up.

### Windows testing on macOS (no PC / no Wine)

`scripts/win-vm/` cross-compiles the **x64** Windows DLL on macOS (`clang-cl` + `lld-link` + `xwin` + WTL) and runtime-tests it in a headless Windows 11 ARM64 QEMU/HVF guest. `setup-mac-toolchain.sh` (once) → `fetch-win11-arm.sh` (build ISO) → `win-vm.sh install` (unattended install) → `win-vm-test.sh --launch` (build → deploy over SSH → relaunch). See `scripts/win-vm/README.md`. clang can't cross-compile ARM64EC (MSVC-only intrinsics); the x64 build runs under emulation on ARM foobar, which is sufficient for UI testing — CI still builds the real ARM64EC binary.

### Versioning + dev loop

Single source of truth for the version is `version.txt` (tracked, e.g. `1.0.3`). The Xcode "Generate Version Header" build phase reads it on every build (declared `alwaysOutOfDate = 1` + listed in `inputPaths`) and writes `version_generated.h` (gitignored) used by `main.cpp` and `install-macos.sh`.

```bash
./scripts/mac-dev-build.sh                # bump patch, xcodebuild Release, install-macos.sh
./scripts/mac-dev-build.sh --minor        # bump minor (resets patch to 0)
./scripts/mac-dev-build.sh --major        # bump major (resets minor + patch)
./scripts/mac-dev-build.sh --no-bump      # rebuild + install with current version (no bump)
./scripts/mac-dev-build.sh --no-install   # bump + build only (skip install-macos.sh)
./scripts/mac-dev-build.sh --new-release  # bump, build, install, then gh release create
```

`install-macos.sh` still works standalone (assumes a build already exists in DerivedData) — `mac-dev-build.sh` is the wrapper that builds first.

### Release pipeline

Automated via `.github/workflows/release.yml` on every push to `main`. Uses [semantic-release](https://semantic-release.gitbook.io/) (config in `.releaserc.json`) reading [Conventional Commits](https://www.conventionalcommits.org/):

- `feat:` → minor bump · `fix:`/`perf:`/`refactor:` → patch bump · `chore:`/`docs:`/`style:`/`test:`/`ci:` → no release · breaking change footer or `!` → major bump.
- Plugin chain: `commit-analyzer` → `release-notes-generator` → `changelog` (writes `CHANGELOG.md`) → `exec` (calls `mac-ci-build.sh <version>` which runs xcodebuild + packages `foo_navidrome_<version>.fb2k-component`) → `git` (commits `version.txt` + `CHANGELOG.md` with `[skip ci]`) → `github` (creates release with the `.fb2k-component` attached).
- SDK source: the workflow clones `marc2k3/foobar2000-sdk` and `marc2k3/pfc` into the sibling-directory layout the project expects (`pfc/`, `foobar2000/{SDK,helpers,shared,foobar2000_component_client,helpers-mac,foo_navidrome}`).
- First-time setup: tag the current state (`git tag v$(cat version.txt) && git push --tags`) so semantic-release has a starting reference; otherwise it treats the next release as `v1.0.0`.

### Manual release (fallback, bypasses CI)

```bash
./scripts/mac-dev-build.sh --new-release    # bump, build, install, package, gh release create
```

## Decisions & Constraints

- **Media Library integration: native via custom URI + library_viewer.** foobar2000's *Preferences › Media Library › Music Folders* only accepts filesystem paths — there is no public SDK hook to register a remote source. The native-feeling integration uses two SDK extensions:
  1. `input_singletrack` for the `navidrome://track/<id>?title=...&artist=...&album=...&tracknumber=N&date=YYYY&duration=SEC&coverArt=...&suffix=mp3&rating=N&starred=1` URI scheme. Metadata is embedded in the URI so playlists render without a network round-trip; the actual HTTP stream URL is resolved at decode time from current credentials, so playlists survive credential rotation / server URL changes. Implemented in `NavidromeInput.mm`. Every parameter is optional and omitted when unset — a URI written by an older version parses with the new fields at their defaults, so the scheme only ever grows.
  2. `library_viewer` registration in `NavidromePlugin.mm` — the browser appears in *Preferences › Media Library › Library viewers* and can be activated from there.

- **Embedded browser: three mount points, one `NSViewController` class.** `NavidromeBrowserController` is mounted three ways, each creating its own fresh instance (Cocoa requires a single superview per `NSView`, so the previous shared-singleton pattern would break multi-mount): (1) directly as the content of the *Preferences › Media Library › Navidrome* sub-page (`preferences_page_navidrome_library::instantiate()`); (2) wrapped in a standalone `NSWindow` by `NavidromeShowStandaloneBrowser()` (File menu / `library_viewer.activate()`); (3) as a dockable panel inside the main window layout via `ui_element_mac_navidrome` (`NavidromePlugin.mm`) — registered under `guid_ui_element_mac`, findable in *Preferences › Display › Layout › Edit Layout* as "Navidrome". All three call `[NavidromeBrowserController new]` fresh; data sharing happens at the model layer (`SubsonicClient` singleton), not the VC.

- **Input handler is registered as a redirect** (`input_entry::flag_redirect`) and opens nested decoders via `g_open_for_decoding(..., fromRedirect=true)` to prevent recursion. This keeps us from duplicating MP3/FLAC/OGG decode logic — foobar's built-in HTTP input does the heavy lifting.

- **Enter in the browser tree replaces the active playlist; double-click and the Add/Play buttons still append.** Both platforms thread a `clearFirst` bool through the add/enqueue chain (Mac: `addNodesToPlaylist:play:closeWhenDone:clearFirst:` → `enqueueNodes:play:clearFirst:`; Windows: `queueSelected(play, closeAfter, clearFirst)` → `enqueueNodes(songs, play, clearFirst)`), defaulting to `false` everywhere except the Enter/`NM_RETURN` path (`commitSelectionFromKeyboard` / `OnTreeReturn`), which passes `true` and calls `playlist_manager::playlist_clear(pl)` before `playlist_add_items`. Only the active playlist's contents are cleared — no other playlists are touched.

- Album art is implemented as a full `album_art_extractor` (NOT `album_art_fallback`) in `NavidromeArtExtractor.mm` — returning true from `is_our_path()` guarantees foobar calls `open()`, which is more reliable than fallback for streamed content. `is_our_path` matches both `navidrome://` URIs (current) and legacy `/rest/stream.view` HTTP URLs (for old playlists). The extractor's `open()` resolves the art id from, in priority order: `coverArt=` query param, `id=` query param, or the `<id>` segment of `navidrome://track/<id>`. The id is then passed to Subsonic's `getCoverArt.view` endpoint — which serves embedded ID3 art if present, otherwise the album folder's `Folder.jpg` / `cover.jpg`.

- **`.fb2k-component` multi-arch layout.** One zip ships every platform: macOS bundle under `mac/`, Windows x86 DLL at the **zip root**, x64 under `x64/`, native Windows-on-ARM under `arm64ec/`. foobar picks the binary at load time, preferring `arm64ec/` on ARM and falling back to x64 emulation if it's absent — so the arm build is a perf upgrade, not a correctness requirement. ARM target is **ARM64EC** (ABI-compatible with x64), NOT pure ARM64. Build adds a 3rd MSBuild target in `build-windows.yml`; `release.yml`'s merge-component folds the DLL in. Touching the arch set means updating both workflows AND the `ProjectConfiguration`/Configuration `PropertyGroup` list in `Windows/foo_navidrome.vcxproj` (only Win32/x64/ARM64EC defined; SDK projects already ship ARM64EC@v143). The windows-2022 runner preinstalls the v143 ARM64 tools + `VC.ATL.ARM64`, so no `vs_installer modify` is needed — but don't move off windows-2022 without re-checking that.

- Linux is intentionally unsupported (foobar2000 has no Linux build).

- **Windows theming is two independent axes — Dark Mode and Colours/Fonts — and `BrowserWindow` now syncs both.** [Issue #4](https://github.com/santiagorod92/foo_navidrome/issues/4) reported the browser staying stock white/black while the host ran foobar's classic orange-on-black "Colours and Fonts" scheme; that scheme is a separate SDK surface from OS Dark Mode, and fixing one doesn't fix the other.
  1. **Dark Mode** (native control chrome + title bar): `fb2k::CCoreDarkModeHooks` (`SDK/coreDarkMode.h`) — header-only, talks to foo_ui_std's dark-mode implementation over a service interface, no `.cpp`/binary-size cost, auto-follows the live toggle (`createAuto()`, the default ctor). Member `m_darkMode`, `m_darkMode.AddDialogWithControls(*this)` at the end of `OnCreate`.
  2. **Colours and Fonts** (Preferences › Display, e.g. custom orange-text/black-bg): `ui_config_manager::query_color(ui_color_text / ui_color_background, t_ui_color&)` (`SDK/ui_element.h`) — works from a plain window, not just `ui_element` panels, per the `CListControlFb2kColors` pattern (`foobar2000/helpers/CListControlFb2kColors.h`) that inspired this. `BrowserWindow::refreshThemeColors()` queries both GUIDs, falls back to system colors for whichever one the user hasn't overridden (`query_color` returns `false`), pushes the result into the tree (`SetBkColor`/`SetTextColor`, or `-1` to revert to default), and repaints the search box / status label / window backdrop via `WM_CTLCOLOREDIT` / `WM_CTLCOLORSTATIC` / `WM_ERASEBKGND` with a cached `HBRUSH`. `BrowserWindow` privately inherits `ui_config_callback_impl` and overrides `ui_colors_changed()` to re-sync live when the user edits the scheme. Native push buttons are left unstyled — Win32 ignores `WM_CTLCOLORBTN`'s brush for `BS_PUSHBUTTON`, so they can't be recolored without full owner-draw.
  Any new top-level or embedded Windows window (e.g. a future headers/settings window) needs both hookups or it will visually clash with the host's configured look.

Required for the official components listing: we can't re-license the SDK.

- The Subsonic salt is stored in `cfg_salt` with default `"fb2k_navidrome"` — kept configurable so token reuse can be invalidated if needed.

- GUIDs for all services live as `static constexpr GUID` in the namespace that registers them. The input handler's GUID is in `NavidromeInput.mm`; the others are in `NavidromePlugin.mm` (lines 17-30). Must be regenerated when forking the component.

## Gotchas

- **`insertNode` (Windows, `BrowserWindow.cpp`) never removes existing tree items — it's a pure append.** The original search implementation reused `populateRoot`/`m_rootNodes` (the same path as the browse tree) without ever calling `DeleteAllItems()`, so every search appended a fresh batch of song rows on top of whatever was already there instead of replacing it — visually "stuck" no matter how the query changed, and clearing the box only restored the browse tree if `m_rootNodes` happened to be empty (never true once you'd searched, since search had overwritten it). Fixed by giving search its own state (`m_isSearching` / `m_searchResultNodes`) that never touches `m_rootNodes`, so category invalidation (`invalidatePlaylistsCategory` etc.) and the startup rating refresh — both of which scan `m_rootNodes` — keep seeing the real tree even mid-search. `restoreBrowseTree()` re-renders from `m_rootNodes` with no network round-trip when the box is cleared. Mac's `_isSearching`/`_filteredNodes` split already worked this way — Windows was the one with the bug.

- **Mac's `NSSearchField.action` alone only fires on Enter or the Cancel button, not per keystroke.** `searchChanged:` was wired as the field's `target`/`action` with nothing else, so "live" search only ever ran when the user pressed Enter — typing itself did nothing until then. Live-as-you-type needs `-controlTextDidChange:` via `NSSearchFieldDelegate` (`_searchField.delegate = self`); both platforms now debounce that (300ms Windows `SetTimer`, 0.3s Mac `NSTimer`) rather than firing a request per character, and both guard applying a response with a generation counter so a slow/out-of-order response from an earlier keystroke can't clobber a newer one.

- **Every `SubsonicClient.h` model class (`SubsonicArtist`, `SubsonicAlbum`, `SubsonicSong`, `SubsonicPlaylist`, `SubsonicGenre`, `SubsonicBookmark`, `SubsonicRadioStation`, ...) needs a matching `@implementation ... @end` block in `SubsonicClient.mm`, even if empty/just a `-description` override.** An `@interface` alone declares the class but emits no `_OBJC_CLASS_$_...` symbol — `[[SubsonicBookmark alloc] init]` then compiles fine but fails at **link** time (`Undefined symbols for architecture arm64: "_OBJC_CLASS_$_SubsonicBookmark"`), not compile time, so it only surfaces in CI/Xcode build, not a quick syntax check. Root cause of a broken `main` build after PR #6 merged (bookmarks feature) — `SubsonicBookmark` had properties + usages but no `@implementation`.

- **`MediaEnrichmentLogic.cpp` / `EsLyricBridge.cpp` must stay `<PrecompiledHeader>NotUsing</PrecompiledHeader>` in `foo_navidrome.vcxproj`.** The rest of `Windows/*.cpp` uses the shared `stdafx.h` PCH. `MediaEnrichmentLogic.cpp` deliberately doesn't include `stdafx.h` at all (kept SDK-free so `tests/MediaEnrichmentTests.vcxproj` and `make mac-test` can compile it standalone, no foobar SDK/PCH involved); `EsLyricBridge.cpp` does include `stdafx.h` but is marked `NotUsing` to match. Don't "clean up" either without checking both project files still build.

- **Transcoding changes the codec, so the decoder hint has to follow.** `cfg_stream_format` is appended to `stream.view` as `format=`, which means a FLAC track can arrive as mp3. Both input handlers pass the track's suffix through `navidrome::effectiveStreamSuffix()` before building the `track.<suffix>` hint for `g_open_for_decoding` — hinting the *stored* codec would pick the wrong decoder. `"raw"` and `""` both mean "original file", so they leave the suffix alone. The hint only matters on the custom-headers path (where we open the stream ourselves); without headers foobar sniffs Content-Type.

- **`songIndexToRemove` is positional and evaluated per request**, so removals are sent **highest index first** (`removeIndexes:fromPlaylist:` / `removeFromPlaylist`). Ascending order would shift every later index by one as the earlier entries disappear — and with >50 removals the chunking makes that a silent wrong-track deletion, not just a failure.

- **A `preferences_page`'s `get_parent_guid()` can point at another page's own GUID, not just an SDK branch GUID (`guid_tools`/`guid_media_library`), to nest it as a visible child under that page.** First used by the Radio Stations sub-page (`preferences_page_navidrome_radio` on Mac, `NavidromeRadioPrefsFactory` on Windows), whose `get_parent_guid()` returns `guid_prefs_page` (the main Navidrome credentials page's own GUID, tail `0x05`) instead of `guid_tools` — it shows up nested under "Navidrome" in the Preferences tree rather than as a sibling of it. Both platforms hardcode the literal parent GUID bytes at the point of use rather than sharing an `extern`, same convention `NavidromeLibraryPrefsFactory` already used for `guid_library_prefs`.

- **Resume-from-bookmark needs a "seek when ready" poll — `playback_control::playback_seek()` can't be called right after `start()`.** The stream isn't necessarily seekable the instant playback begins, and there was no existing seek call anywhere in the codebase before the Bookmarks feature. Both `BrowserWindow::enqueueNodes` (Windows) and `NavidromeBrowserController`'s equivalent (macOS) poll `playback_control::playback_can_seek()` on a short-lived background thread (~100ms interval, ~3s timeout) after `start()`, then call `playback_seek()` back on the main thread. Reuse this helper (`BrowserWindow::seekWhenReady` on Windows) for any future "jump to position" feature instead of calling `playback_seek` directly after `start()`. Also: Subsonic reports/accepts bookmark `position` in **milliseconds**; `playback_get_position()`/`playback_seek()` are in **seconds** — convert at the boundary (`NavidromeNode::bookmarkPositionMs` stores the raw ms value from the server).

- **Radio stations bypass the `navidrome://` URI scheme and the custom-headers path entirely.** Every other browsable leaf (songs, bookmarked songs) is enqueued as a `navidrome://track/<id>` URI so the redirect input handler (`NavidromeInput.mm` / `NavidromeInputWin.cpp`) can resolve the live authenticated stream URL and apply custom headers at decode time. Radio stations instead get their raw `streamUrl` set directly as the `playable_location_impl` path — `g_is_our_path` only matches the `navidrome://track/` prefix, so a plain `http://`/`https://` station URL is never routed through our input handler; foobar's stock HTTP input plays it (including any Shoutcast/Icecast metadata) with zero custom code. Practical consequence: a station's stream does **not** carry whatever custom HTTP headers the user configured for their Navidrome server (e.g. Cloudflare Access tokens) — that's inherent to how Subsonic radio stations work (the stream URL is whatever the server operator configured, not a Navidrome-proxied URL), not a bug to fix.

- **`createInternetRadioStation.view` doesn't echo the new station's id back**, unlike `createPlaylist.view`. Both `SubsonicClient`'s `createRadioStationWithStreamURL:name:homePageUrl:error:` (macOS) and `SubsonicClientWin::createRadioStation()` (Windows) therefore always return `""` on success, mirroring the existing "empty id, no error = success" convention `createPlaylistNamed:`/`createPlaylist` already use for their own no-id edge case — callers must check the error output, not treat an empty return as failure.

- **Random Mix is a context-menu action, not a category node — a category node placed above the artist list never showed up in Windows/Wine local testing, root cause never pinned down.** First implementation added `CatRandomMix`/`NavidromeCategoryRandomMix` to the smart-list category array (same pattern as Starred/Genres/Radio) with title `"\U0001F500 Random Mix"` (🔀, U+1F500, a non-BMP surrogate pair, unlike the BMP `"★ Starred"` which is known to render fine). It never appeared in the tree under Wine — not tofu, the whole row was missing — even after dropping the emoji for a plain-ASCII title, which ruled out the surrogate-pair theory as the actual cause. Rather than keep debugging a Wine-only rendering path with no repro insight, the feature was moved to a right-click context-menu item ("Random Mix", alongside "Send Active Playlist to Navidrome") on both platforms — same pattern as "Play Similar", fetches on click instead of rendering a persistent node. If a future smart-list category node also silently fails to render, don't assume it's the same bug (emoji or otherwise); the actual mechanism was never confirmed, only worked around.

- **`make win-build`/`win-build-local.sh` (no flag) installs the DLL but does not restart the local Wine foobar2000 — components load only at process startup, no hot-reload.** A DLL replaced under a still-running `foobar2000.exe` (Wine, same as macOS codesigning — see the `mac-dev-build.sh` gotcha below for the Mac equivalent) is silently ignored until the process restarts, which looks exactly like "my change isn't in the build." Use `make win-build-launch` (or `win-build-local.sh --launch`) to build, install, and relaunch in one step.

- **`scripts/win-build-local.sh`'s object cache is keyed on mtime only, not on flags/headers — a stale `.obj` can silently produce an ABI-mismatched binary that crashes at runtime instead of failing to build.** Hit while testing the Colours-and-Fonts sync fix: adding `#include <SDK/ui_element.h>` + a new base class to `BrowserWindow.h` compiled fine incrementally, but the resulting DLL crashed instantly on `BrowserWindow::get().show()` (`EXCEPTION_ACCESS_VIOLATION` reading offset 8 off a null pointer — a `this`-pointer-adjustment fault from a stale object built against the old class layout). A full `--clean` rebuild fixed it with zero code changes. Symptom to watch for: a crash that only reproduces from the locally-built `build-win/` DLL and can't be explained by the diff — try `--clean` before chasing a phantom logic bug. foobar2000's own crash reporter (`~/.foobar2000/profile/crash reports/failure_*.txt`) gives module+offset even when Wine's own SEH trace is a red herring; symbolize it against a `/Z7 /debug:full` rebuild with `llvm-symbolizer --obj=foo_navidrome.dll --relative-address -f -C <offset>` (add those two flags to `CL_COMMON`/the `lld-link` line temporarily — don't leave them in, they're debug-only and bloat the DLL ~25%).

- **Reading the tree control off the UI thread is a cross-thread call.** `BrowserWindow::selectedNodes()` walks the `CTreeViewCtrl`, so every background action captures the selection on the UI thread first and passes the `vector<shared_ptr<NavidromeNode>>` into the worker (see `collectSongIdsDeep`, which deliberately takes pre-captured nodes rather than calling `selectedNodes()` itself). The same rule applies on macOS to `-selectedNodes` / `-parentForItem:`.

- **`cfg_int` has the same legacy/modern ambiguity as `cfg_bool`** — write `cfg_var_modern::cfg_int` (used by `cfg_max_bitrate`). Unqualified it resolves to `cfg_var_legacy::cfg_int_t<t_int32>`, which has no `set()` and serializes differently.

- **`cfg_bool` must be written as `cfg_var_modern::cfg_bool`.** Unqualified, it resolves to the legacy `cfg_var_legacy::cfg_int_t<bool>` on the Windows SDK headers — which has no `set()`, so the Windows build fails while macOS (where the modern one wins) compiles fine. The two flavours also serialize differently, so a var declared as legacy on one platform and modern on the other would not round-trip. `cfg_string` happens not to have this ambiguity; `cfg_bool` does. Applies to `cfg_scrobble` in `NavidromePlugin.mm` / `NavidromePluginWin.cpp` and its `extern` in `Mac/NavidromePreferencesController.mm`.

- **`std::min` / `std::max` need parens on Windows: `(std::min)(a, b)`.** `windows.h` defines `min`/`max` as macros, so a bare `std::min(...)` expands into garbage and fails with a bewildering `error: expected unqualified-id`. macOS compiles the same line fine, so this only shows up in the Windows/CI build.

- **`scripts/win-vm/build-mac.sh` hardcodes SRCS too — same trap as `win-build-local.sh` below.** It was missing `MediaEnrichmentLogic.cpp` and `EsLyricBridge.cpp` entirely (added to the vcxproj later, never to this script), so the mac cross-build linked with a wall of undefined symbols until they were added. When you add a `Windows/*.cpp`, update **three** places: `foo_navidrome.vcxproj`, `scripts/win-build-local.sh`, and `scripts/win-vm/build-mac.sh`.

- **`scripts/win-build-local.sh` hardcodes its own component source list (SRCS) instead of reading `foo_navidrome.vcxproj`.** Adding a new `Windows/*.cpp` to the vcxproj (CI/MSVC build) does NOT make it visible to the local clang-cl/Wine build — it silently compiles without it and fails at link time with a wall of undefined symbols. When you add a source file, add it to both `foo_navidrome.vcxproj`'s `ClCompile` `ItemGroup` AND the `echo "$REPO/Windows/....cpp"` lines in `win-build-local.sh`.

- **Cover-art cache (`CoverCache`) and the ESLyric bridge config both need explicit invalidation on credential/header changes** — they're keyed/generated from server URL + username + token at the time of the last save, not read live. `NavidromePluginWin.cpp` calls `CoverCache::instance().clear()` and re-runs `EsLyricBridge::installOrUpdate()` in both `NavidromeHeadersWindow::OnSave` and `NavidromePrefsInstance::apply()`. If you add another place credentials/headers can change, wire the same two calls in or covers/lyrics will silently keep using stale auth.

- **`install-macos.sh` must prefer Release over Debug builds.** DerivedData often contains a stale Debug `.component` from past Xcode builds. The script filters by `*/Products/Release/*` first, then sorts by mtime descending. If you change build configurations, audit `find_component()` in `install-macos.sh`.

- **`set -u` + empty bash arrays.** macOS ships bash 3.2 which treats `"${EMPTY_ARRAY[@]}"` as an unbound variable under `set -u`. `mac-dev-build.sh` avoids this with explicit if/else around `./install-macos.sh` invocation rather than building an array of args. Same trap applies to any new shell helpers — either use explicit conditionals or `"${ARR[@]+"${ARR[@]}"}"`.

- **Never run `mac-dev-build.sh` / `install-macos.sh` while foobar2000 is running — it kills the running instance with a crash that looks like yours.** macOS validates each code page against the bundle's signature the first time it's faulted in. Replacing and re-signing the `.component` under a live process leaves it mapped to a file whose pages no longer match, so the next page it touches gets `EXC_BAD_ACCESS (SIGKILL (Code Signature Invalid))`, `Termination Reason: Namespace CODESIGNING, Code 2, Invalid Page`, and a kernel triage line reading "A memory corruption was found in executable text". The crash report points at whatever function happened to live on that page — in one instance `mainmenu_navidrome::instance_create + 0`, reached while AppKit was populating a right-click menu, which read exactly like a bug in the context-menu code that had just been written. Tells it apart from a real crash: the termination namespace is CODESIGNING (application code cannot produce that), and the fault is an instruction abort at offset `+ 0` of some function. Quit foobar2000 before installing.

- **Bundle directory mtime doesn't update on `cp -Rf`.** When verifying an install, check the inner binary (`Contents/MacOS/foo_navidrome`), not the `.component` directory itself — `stat` on the directory shows the original mtime even after a fresh copy.

- **`library_viewer` surfacing on foobar2000 v2 Mac.** There is NO unified "Library viewers" list page in Preferences. Instead, each `library_viewer` is expected to register its own `preferences_page` parented to `preferences_page::guid_media_library` — that page becomes the entry point that appears under *Preferences › Media Library*, alongside Album List / ReFacets. Our component does both: a config page parented to `guid_tools` (credentials) AND a `guid_media_library` sub-page (`preferences_page_navidrome_library` in `NavidromePlugin.mm`) with an "Open Navidrome Browser" button + status. Users diagnosing "I don't see Navidrome in my Media Library" should check (1) foobar fully restarted, (2) *Preferences › Components* shows the component loaded OK, (3) `View › Console` for registration errors.

- **`library_viewer.get_preferences_page()` must point to the Media-Library-parented page**, not the Tools-parented one — that's how foobar wires the viewer into the Media Library navigation. In our code it returns `guid_library_prefs`, not `guid_prefs_page`.

- **Debugging input/decode failures.** No straightforward debugger attach for foobar2000 components (Mac or Wine), so logging is the primary diagnostic channel. `decode_initialize` on both platforms already emits `NAVIDROME_LOG("Input", …)` / `NAVIDROME_ERR` at each step (URL resolution, `g_open_for_decoding`, decoder ready) — the user-visible "Unsupported format or corrupted file" is a generic foobar translation that doesn't pinpoint the failing step, these lines do. They stay in permanently (no-op in release); use `make win-logs` / `make mac-logs` to watch them.

- **Crash-resilient logging comes for free from `NavidromeDebugLog.h`'s tracer** — `navidrome::dbg::line()` does `fopen`/`fprintf`/`fclose` per line, so a line survives even a hard crash mid-decode (unlike `console::print`, whose panel never flushes on crash). This replaced the old ad-hoc `navi_log` helper. Symbolizing a crash offset is separate — see the local-build `--clean` gotcha for the Windows path.

- **Local dev-loop tracing (both platforms): the `NAVIDROME_LOG` / `NAVIDROME_WARN` / `NAVIDROME_ERR` macros in `NavidromeDebugLog.h` (repo root, cross-platform, header-only), gated on `NAVIDROME_DEBUG_LOG`.** `View › Console` needs eyes on the GUI, impractical for a headless Wine host and noisy on Mac — so when the flag is on the tracer `fopen`-appends `foo_navidrome_debug.log` in the host `/tmp` (Windows/Wine writes it as `Z:\tmp\…`, which Wine maps to host `/tmp`; macOS writes `/tmp/…` directly), one line as `HH:MM:SS.mmm  LEVEL  TAG  message` plus a `==== trace session … ====` banner on first write. Timestamp source is `GetLocalTime` on Windows, `gettimeofday`+`localtime_r` elsewhere. Tags: `UI` (`BrowserWindow` — old bare `dbgLog("msg")` sites still work via a one-line shim → `NAVIDROME_LOG("UI", …)`), `HTTP` (Subsonic client request + outcome: `SubsonicClientWin::httpGet` / `SubsonicClient.mm -fetchJSON:`), `API` (Subsonic `status != ok`), `Input` (`NavidromeInputWin` / `NavidromeInput.mm` `decode_initialize` steps). URLs go through `navidrome::dbg::scrubAuth()` first — redacts `t`/`s`/`p`/`u` query values so the token never lands in a world-readable file. **Any new log line that prints a URL must call `scrubAuth` on it** — easy to miss on the decode `hint`, which is the raw stream URL (with token) unless a `track.<suffix>` hint replaced it. Names are spelled out in full (`NAVIDROME_*`, `NavidromeDebugLog.h`, `navidrome-logs.sh`) to match the existing `NAVIDROME_RATING` / `Navidrome*` convention — no `Navi` abbreviation.
  - **Windows:** `scripts/win-build-local.sh` passes `/DNAVIDROME_DEBUG_LOG=1`; `Windows/foo_navidrome.vcxproj` (MSBuild/CI) never does. `--launch` truncates the log and prepends a `==== build <version> installed … ====` marker.
  - **macOS:** `scripts/mac-dev-build.sh` passes `OTHER_CFLAGS='$(inherited) -DNAVIDROME_DEBUG_LOG=1'` — **except** on `--new-release`, which must match the `mac-ci-build.sh` binary exactly (a released build has no tracing). It truncates + version-marks the log after `install-macos.sh`.
  - `make win-logs` / `make mac-logs` both run `scripts/navidrome-logs.sh` (platform-neutral colourised `tail -F`; `ARGS=-a` for the whole file).
  - When the flag is undefined the macros expand to a type-checked `sizeof` no-op — zero cost, nothing ships. `scripts/win-vm/build-mac.sh` doesn't define it either (matches release). `NavidromeDebugLog.h` is **header-only on purpose** — it is NOT added to any build source list (`foo_navidrome.vcxproj` ClCompile, `win-build-local.sh`, `win-vm/build-mac.sh`). Call sites are free to leave in permanently; add new ones sparingly (free in release, still local-log noise).

- **`navidrome://track/<id>` URI parsing — host vs path trap.** RFC-3986 says `scheme://X/Y` puts `X` in the authority (host) component and `/Y` in the path. So `NSURLComponents` on `navidrome://track/abc123` gives `host=track`, `path=/abc123`. Splitting `path` on `/` yields only 2 components (`["", "abc123"]`), not 3 — `parse_uri` in `NavidromeInput.mm` strips the leading `/` from `percentEncodedPath` and uses that as the song id. The literal string `track` in the URI is part of the prefix-match check in `g_is_our_path`, not a path segment we parse out. If extending the scheme with more "sub-paths" (e.g. `navidrome://playlist/<id>`), make the dispatcher inspect `c.host` rather than path segments.

- **`get_info()` is NOT the display path for a freshly enqueued track — the hint list is.** Both `enqueueNodes` implementations push a `file_info_impl` into a `metadb_hint_list` before the items land in the playlist, which populates metadb and means foobar never calls `get_info()` for them. Any field you add to `get_info()` must be added to the hint block too, or it stays blank until the user forces an info reload. The pre-existing `codec` field demonstrates the failure: it's set in `get_info()` but not in the hint, so the Codec column is empty for newly added tracks. `NAVIDROME_RATING` / `NAVIDROME_STARRED` are set in both places for this reason.

- **Don't name an exported title-formatting field `rating`.** foobar2000's own Playback Statistics provides `%rating%` (and `%play_count%`, `%last_played%`, …) through `metadb_display_field_provider`, whose header warns that overlaying a standard field has "severe ill effects" and that two providers of the same name are undefined behaviour. Precedence between a `meta_set("rating", …)` field and that provider is undocumented. The server-side values are therefore exported under the `NAVIDROME_` prefix (`NavidromeRatingTag` / `NavidromeStarredTag` in `NavidromeInput.mm`, `navidrome::kRatingTag` / `kStarredTag` in `NavidromeInputWin.cpp`). Same reasoning applies to any future exported field.

- **A URI-embedded value can only be refreshed through metadb, never by rewriting the URI.** Adding or changing a query parameter changes the `playable_location`, so the same song enqueued with `rating=5` and later with `rating=4` is two distinct metadb items — a "rewrite the URI" refresh would silently duplicate playlist entries instead of updating them. foobar's own "Reload info" is no help either: it calls `get_info()`, which re-reads the same immutable URI. `syncRatingsToPlaylists()` therefore uses `metadb_hint_list_v3::add_hint_forced()`, which updates metadb's cached info for the existing item and leaves the URI alone. Forced rather than a normal hint because a normal one is skipped when the file hasn't changed by timestamp — and a URI never does. Consequence to know: metadb and the URI now disagree, so a user-forced full info reload falls back to the enqueue-time snapshot. That's a regression to an older value, never to garbage.

- **The rating refresh must not sit behind `cfg_scrobble`.** Both scrobblers extract the song id in `on_playback_new_track`, which used to return early when scrobbling was off. The rating refresh is a display concern, not a play report, so the id extraction and `refreshRatingAsync()` now run *before* the scrobble gate. Anything else added to that callback needs the same consideration.

- **The startup refresh groups by album, and that's the only thing that makes it affordable.** `getSong.view` takes a single id and OpenSubsonic has no multi-id or all-rated-songs endpoint, so a per-track refresh is one request per playlist entry. `getAlbum.view` returns `userRating` for every song of an album in one request, so `scanPlaylistAlbums()` collapses the pass to one request per *distinct album*. That is the only reason `albumId=` is in the URI — the input handler never reads it back. Entries written before it existed can't be grouped and are skipped (counted and reported, never swallowed); they still catch up via rate/star, browse and playback, and a sibling entry from the same album that does carry an `albumId` drags them along, because the sync matches on song id, not album.

- **`init_stage_callback` is never dispatched on macOS — an `FB2K_ON_INIT_STAGE` hook there silently never fires.** The startup rating refresh was first written as `FB2K_ON_INIT_STAGE(func, init_stages::after_ui_init)`, which is the documented one-liner and works on Windows (the dispatch comes from `foo_ui_std`). On foobar2000 v2.25.10 for Mac it produced no call at all: the component was loaded, the strings were in the binary, the playlists were populated, and nothing ran. There is no error and no console output — the failure mode is pure silence, which is why it cost a build/restart cycle to find. Use `initquit::on_init` instead; it fires on both platforms, and playlists are already loaded by then (foobar's own startup log prints "Playlist #N loaded" before our `on_init` line). Applies to any future startup hook, not just this one.

- **Report skipped coverage, stay quiet about states the user chose.** The startup refresh has four ways to do nothing. Two of them — the switch is off, no server is configured — are states the user set, and logging those on every start is noise. The other two leave playlist entries behind, and a partial refresh is indistinguishable from a complete one unless it says so, so those print: how many entries carry no album id, and how many were skipped alongside a successful run. The fully silent case is a profile with no `navidrome://` tracks at all.

- **The startup switch is an `advconfig_checkbox_factory`, not a `cfg_bool` plus two dialogs.** Its request count scales with how many distinct albums the playlists span, so it needs an off switch — but a `cfg_bool` would mean UI work in `NavidromePreferencesController.mm` *and* the Windows prefs dialog. One line in `main.cpp` gives both platforms the checkbox under *Preferences › Advanced › Tools*, and dodges the `cfg_var_modern::cfg_bool` ambiguity entirely.

- **Any code that consumes `navidrome://` URIs must be updated when the scheme changes.** The art extractor's `is_our_path` originally only matched the legacy `/rest/stream.view` HTTP URLs and silently stopped working when we moved to `navidrome://` URIs — symptom was missing cover art in Now Playing with no error. Audit `strstr`/`strncmp` calls in `*.mm` whenever the URI scheme is touched.

- **`NSViewController` for multi-mount UIs in foobar2000.** Foobar's macOS preferences pages take an NSObject wrapped via `fb2k::wrapNSObject(...)`; passing an `NSViewController` works directly. Same pattern for `ui_element_mac::instantiate()` — it also just returns a wrapped `NSViewController`. To also expose the same UI as a standalone window (menu / `library_viewer.activate()`), create the VC and set `window.contentViewController = vc`. Do NOT share a single VC instance across multiple mount points — Cocoa requires each `NSView` to have a single superview, so a shared VC's `view` can only be parented to one host at a time. Each mount creates its own VC; data sharing happens at the model layer (`SubsonicClient` singleton). `ui_element_mac`'s layout system may call `instantiate()` more than once per session too (e.g. the user docks the panel, undocks, redocks, or splits the layout) — never cache a VC across calls.

- **Release-loop prevention.** semantic-release commits `version.txt` + `CHANGELOG.md` back to `main` after a successful release. Without guarding, that push would trigger the workflow again. Two layers of protection: (1) the release commit message contains `[skip ci]`, and (2) `release.yml` has `if: "!contains(github.event.head_commit.message, '[skip ci]')"` — both must remain in sync. The workflow also uses `concurrency: { group: release-${{ github.ref }} }` so two releases can't race on the same tag.

- **`mac-dev-build.sh` vs `mac-ci-build.sh` — keep them separate.** `mac-dev-build.sh` is the local developer loop: bumps `version.txt`, builds, **installs locally** to `~/Library/foobar2000-v2/`, packages. `mac-ci-build.sh` is for the GitHub Actions runner: receives the version as an arg (from semantic-release), builds into a hermetic `build/derived/` path, packages — and crucially does NOT touch `~/Library` (which on a runner would create a phantom dir). Don't merge them.

- **PCH compile fails on older Xcode with `std::string_view`/`std::string` errors.** `pfc/string-interface.h` uses `std::string` and `std::string_view` without `#include <string>` / `<string_view>` — it relies on transitive includes from libc++. On Xcode 26 + macOS 26 SDK those transitively land before pfc; on Xcode 15.4 + MacOSX14.5.sdk (the default on GitHub Actions `macos-14` runner) they do NOT, and the PCH compile of `stdafx.h` fails with two errors:
  ```
  pfc/string-interface.h:49: error: no type named 'string_view' in namespace 'std'
  pfc/string-interface.h:50: error: implicit instantiation of undefined template 'std::basic_string<char>'
  ```
  Fix is to add `#include <string>` and `#include <string_view>` to `stdafx.h` BEFORE `<helpers/foobar2000+atl.h>` — this guarantees both types are complete regardless of the toolchain. Don't try to "fix" pfc upstream; we don't control that fork.

- **`xcodebuild` log handling in CI.** Never truncate xcodebuild output with `| tail` — compile-command echoes scroll the actual `error:` lines off the top, so a failed PCH or single bad symbol shows up as just `** BUILD FAILED **` with no context. Two layers of observability:
  1. `mac-ci-build.sh` redirects the full log to `/tmp/xcodebuild.log`, prints a filtered summary (`error:`/`warning:`/`note:`/`** BUILD`/`ld:`/`fatal:`/`FAILED`) on every run. On failure it dumps the full log and then re-prints `grep -B 3 "error:|fatal error:"` at the very end — GitHub Actions step output is read bottom-up when a job fails, so error lines at the tail are what the eye lands on.
  2. `release.yml` has an `if: failure()` step that uploads `/tmp/xcodebuild.log` as an artifact named `xcodebuild-log` (retention: 7 days), so anyone debugging can download and grep locally without scrolling through truncated GA logs.
  Don't switch to `xcpretty` or similar without preserving both layers — the diagnostic value when CI fails on a Mac build you can't reproduce locally is the whole point.

- **SDK source in CI: `reupen/foobar2000-sdk-unmodified`, not `marc2k3/foobar2000-sdk`.** `pfc/` is NOT a separate GitHub repo — `marc2k3/pfc` is a 404. We tried `marc2k3/foobar2000-sdk` (redirects to `javascript-panel/foobar2000-sdk`) — it contains `SDK/`, `helpers/`, `shared/`, `foobar2000_component_client/`, plus `pfc/`/`libPPUI/`/`columns_ui-sdk/` at the staging root — BUT it does NOT ship `helpers-mac/`, which we need for `NSView+embed.m`. `reupen/foobar2000-sdk-unmodified` is an unmodified mirror of the official SDK and does include `helpers-mac/`. Layout the workflow expects after checkout into `_sdk-staging/`:
  ```
  _sdk-staging/
    foobar2000/                       ← nested wrapper, NOT the target layout
      SDK/  helpers/  helpers-mac/  shared/  foobar2000_component_client/
    pfc/
    libPPUI/
    sdk-license.txt  sdk-readme.html
  ```
  The staging step moves `_sdk-staging/foobar2000/<dir>` → `foobar2000/<dir>` (SDK subdirs are one level deeper than the staging root) and `_sdk-staging/pfc` → `pfc` (this one IS at the staging root). The verify step requires `helpers-mac` in the list and prints `ls -la` of both `_sdk-staging` and `_sdk-staging/foobar2000` on failure so future layout drift is debuggable.

- **Testing the x64 build on ARM foobar (via `scripts/win-vm/`) has three traps** — all in `scripts/win-vm/README.md`, condensed here: (1) `clang-cl` parses a leading `/Users/...` source path as the `/U` flag → pass sources as `/Tp<path>`; (2) the local x64 build **must** use static CRT (`/MT`) — foobar-on-ARM only bundles the ARM64EC flavour of `VCRUNTIME140`/`MSVCP140`, so an emulated x64 `/MD` DLL fails to load silently; (3) install once from a `.fb2k-component` (it lands in `user-components-arm64ec/`), because a loose DLL dropped into a component folder is NOT picked up by the ARM build — after that the DLL can be hot-swapped in place. Also: the QEMU guest needs an audio device (`-device intel-hda`), else playback dies with "Element not found" (0x80070490) before decode.
